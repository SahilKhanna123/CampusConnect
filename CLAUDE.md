Guidance for Claude Code (and other contributors) working in this repository.

## Project Overview

CampusConnect is a trusted community marketplace connecting students, parents, alumni, and travelers moving between a student's home area and college — launching with **Bay Area ↔ UC Irvine**. Users are not permanently a "driver" or "requester": the same account can offer a ride one week and request one the next. Role lives on the action (`Trip`/`Request`), not on the `User`.

## Auth Architecture

Supabase Auth owns account credentials (`auth.users`); Prisma's `User` table is a separate, app-owned table keyed on the **same id** (`User.id = auth.users.id`). Nothing in Prisma generates that id — it's always the Supabase-issued UUID, written by app code.

- **Signup** (`src/app/(auth)/sign-up/page.tsx`, client component) starts with a persona picker (Student / Parent / Alumni / Traveler) that is **NOT a stored/permanent role** (USER != ROLE) — it only decides the post-confirmation redirect. Student/Alumni/Traveler all go through the identical `supabase.auth.signUp()` flow described below and land on `/onboarding` (a soft-nudge profile-completion step, see Profile & Onboarding below — not Home directly); Parent goes through the same signup mechanics but lands on `/family/connect-student` next (see the Parent/Student Linking section below). The signup email itself doubles as the university-verification input for a Student. Confirmation offers **two independent paths**, both leading to the same place:
  - **Link**: the email's `emailRedirectTo: {origin}/auth/callback` link. `src/app/auth/callback/route.ts` exchanges the PKCE `code` for a session, then calls `syncUserFromAuth`.
  - **OTP code**: the sign-up page also shows a numeric code input right after submitting (Supabase's default email OTP is 8 digits — the input's `maxLength` learned this the hard way, don't hardcode a shorter length). The client calls `supabase.auth.verifyOtp({ email, token, type: 'signup' })` directly (no server route involved in the verification itself), then `POST /api/auth/sync` to run the same `syncUserFromAuth` bridge against the now-cookie-authenticated session.
  - **Why both exist:** some university (and corporate) mail gateways pre-fetch every link in incoming email to scan it, which silently consumes the link's single-use token before the real user clicks it — confirmed in this project via a real test where Supabase's own `confirmation_sent_at`/`email_confirmed_at` were 7 seconds apart, not humanly possible. The link still works fine for domains without that behavior; the code is the reliable fallback, since a scanner can't type a code into a form. **For the code to actually appear in the email, the "Confirm signup" template must be edited in the Supabase dashboard (Authentication → Emails → Templates) to include `{{ .Token }}`** — by default Supabase's template only shows the link.
- **`src/lib/onboarding.ts`**'s `syncUserFromAuth(authUser)` is the single place that bridges a confirmed Supabase Auth user into Prisma — both the link and OTP paths call it, so the Prisma-write logic exists exactly once. It upserts the `User` row and `VerificationRecord(type=email, status=verified)` (reaching either path already proves Supabase confirmed the email), then checks the confirmed email's domain against `SupportedUniversityDomain` and upserts `VerificationRecord(type=university, status=verified)` in the same call if it matches — someone who signs up with `you@uci.edu` lands on Home already fully verified, no second step. **Same call also claims-or-creates their `StudentRecord`** via `claimOrCreateStudentRecord` (see the Parent/Student Linking section) — this is what lets a student who signs up later automatically attach to a record a parent already created. This merged design was a deliberate simplification made mid-build (see git history) after the original plan doc's two-step design (separate `.edu` entry post-signup) proved more failure-prone in practice than it was worth.
- **`/verify`** (`src/app/verify/page.tsx`) still exists as a **self-serve fallback**, not the primary path: for anyone who signed up with a personal email and wants to add a university badge later (e.g. an alum, or a student who typo'd their domain at signup). It posts to `/api/verification/university/request` (checks the domain against `SupportedUniversityDomain`, emails a single-use expiring token) and, when landed on with `?token=`, to `/api/verification/university/confirm`. This is one of two paths where `src/lib/email.ts` actually sends an email (the other is the parent-connection OTP/notice emails below) — the merged signup flow never calls it, since Supabase's own confirmation email already covers that trip.
- **`src/middleware.ts`** + **`src/lib/supabase/middleware.ts`** refresh the session cookie on every request — required by the `@supabase/ssr` pattern since Server Components can't write cookies themselves.
- **`src/lib/supabase/client.ts`** / **`server.ts`** are the two Supabase client constructors (browser vs. cookie-reading server); **`src/lib/auth.ts`**'s `getCurrentUser()` is the one place that joins a Supabase session to a Prisma `User` (with `verifications`, `parentLinksAsParent` (incl. nested `studentRecord`), `homeCity`, and `studentRecord` all included) — use it from Server Components/route handlers rather than calling Supabase directly, so verification-badge logic stays in one place (see `isUniversityVerified` / `universityBadgeLabel` / `parentRelationshipBadgeLabel`).
- Login (`/login`) and sign-out (`POST /api/auth/signout`) are minimal, included because an auth setup isn't testable without them — kept intentionally small.

**Two entry gates exist, enforced differently:**
- **Parent-signup accounts (`User.signedUpAsParent = true`)**: cannot reach *any* other page until `hasLinkedStudent(user)` is true (linked to at least one student, any student, via OTP). `/family/connect-student` is the sole exempt path. This is a real, currently-working gate — **but it is enforced in two places, not one, and both are load-bearing**:
  - `src/app/layout.tsx` does the DB-backed check (`hasLinkedStudent(user)` against Prisma) and `redirect()`s — this is what runs on the very first full page load.
  - `src/lib/supabase/middleware.ts` (`updateSession`, called from `src/middleware.ts` on every request) does a *second*, independent check on every navigation, including client-side `<Link>` transitions. This turned out to be necessary, not redundant: Next.js App Router layouts are **not re-executed on client-side navigation** that keeps the same layout, so a gate living only in `layout.tsx` only actually fires on the first load — a gated parent could click straight into Home/Post afterward once past that first render. Middleware can't query Prisma directly here (this project's installed Next.js version does not actually register middleware when `export const config = { runtime: "nodejs" }` is set, despite that being the documented syntax for stable Node.js middleware — confirmed by reproducing an empty `middleware-manifest.json` in `next build` output), so it instead checks a denormalized `hasLinkedStudent: boolean` cached on the Supabase Auth user's `app_metadata`. `src/app/api/family/parent-link/confirm/route.ts` sets that flag to `true` the moment a link is created; `src/app/api/family/link-objection/[token]/reject/route.ts` clears it back to `false` if a revocation leaves the parent with zero non-revoked links. Prisma's `ParentStudentLink` rows remain the actual source of truth (`hasLinkedStudent()` in `src/lib/auth.ts`, used by the `layout.tsx` check and everywhere else) — the `app_metadata` flag is only a fast, edge-readable copy for this one gate.
- **Posting (Trip/Request creation) is implemented; university-verification and on-behalf-of-student posting are still deliberately deferred.** `/api/trips` and `/api/requests` now have working `POST`/`GET`/`PATCH`/DELETE-as-cancel handlers (see the Trip Posting System section below) — but neither checks `isUniversityVerified(user)` yet (a product decision to defer this, made explicitly so testing isn't blocked by unverified test accounts, not an oversight), and every post is self-authored (`beneficiaryId` always equals the poster) since `canActOnBehalfOf(parentUserId, studentRecordId)` (`src/lib/auth.ts`) can't be wired into `Request` creation until the beneficiary-representation fork below is resolved. Messaging (`conversations`) is implemented (see the Messaging section below); the request/trip matching lifecycle (`requests/[id]/{accept,decline,complete}`) remains unimplemented `501` stubs. When that gets built: check `isUniversityVerified(user)` server-side before any student write, and `canActOnBehalfOf` before letting a parent set a Request's beneficiary to someone other than themselves. Don't confuse this finer-grained per-student check with the coarser `hasLinkedStudent` app-wide gate above — they answer different questions ("can this parent act for *this* student" vs. "can this parent use the app *at all*").

## Parent/Student Linking (StudentRecord Architecture)

**Core problem this solves:** a parent may want to use CampusConnect before their student ever creates an account — the old model (`ParentStudentLink` pointing straight at a `User`) made that impossible. `StudentRecord` (`prisma/schema.prisma`) is a student identified by university email that can exist with **no** `User` account at all (`userId` nullable). `ParentStudentLink` now points at `StudentRecord`, not `User` — this is what lets an existing link stay valid automatically once the student eventually signs up, no relinking needed.

- **Duplicate prevention is entirely load-bearing on `StudentRecord.universityEmail` being `@unique`, plus the *pattern* used around it** — see the extensive comments on `claimOrCreateStudentRecord` (`src/lib/onboarding.ts`). Two distinct races matter and are both handled: (1) two concurrent *creates* for the same email (real `@unique`-backed create, with a caught-`P2002`-then-refetch fallback — **not** a naive find-then-create, which would race); (2) two concurrent *claims* of the same unclaimed record (a conditional `updateMany(WHERE userId IS NULL)`, since the `userId @unique` constraint alone only stops one `User` claiming two records, not two claims racing on one record). Both races were verified against the real database during development (concurrent `Promise.all` calls into `claimOrCreateStudentRecord`, confirming a single row results either way) — don't remove that rigor when touching this function; there's no permanent automated test for it yet (no test suite exists in this project), so re-verify by hand if you change it.
- **Every path that can create or claim a `StudentRecord` MUST go through `claimOrCreateStudentRecord`** — never a bespoke find-then-create. Currently two callers: `syncUserFromAuth` (a student's own signup) and `src/app/api/family/parent-link/confirm/route.ts` (a parent's OTP confirm).
- **Parent signup skips email confirmation entirely** — `/api/auth/parent-signup` creates the Supabase Auth user via the admin API (`src/lib/supabase/admin.ts`, service-role key, server-only) with `email_confirm: true`, so a parent never clicks a link or enters a code for their own email; the client immediately calls `signInWithPassword` then `/api/auth/sync`. This is a narrow bypass scoped to that one route, not a project-wide Supabase setting change — the Student path's own confirm flow (link/code, described above) is completely unaffected and stays fully rigorous, since a student's email confirmation doubles as their university verification. A parent's own email isn't the security-critical fact in this product; the student's is.
- **Parent flow**: `/family/connect-student` (parent-facing, two steps on one page) → `POST /api/family/parent-link/request` (caller just needs to be authenticated — no email-verification precondition, per the above — validates the student email's domain against `SupportedUniversityDomain`, creates a `ParentStudentOtpRequest` — an *ephemeral* pending row, deliberately not touching `StudentRecord` yet so a typo'd email never leaves an orphan record — and emails an 8-digit code to the **student's** inbox, not the parent's) → `POST /api/family/parent-link/confirm` (validates the code against a hash with attempt-limiting, then calls `claimOrCreateStudentRecord` and creates `ParentStudentLink(status=otp_verified)`).
- **Why a custom OTP instead of Supabase's**: Supabase's OTP is inherently tied to the auth account being signed into/created for that email — it can't send a code to a third party's inbox on someone else's behalf. `src/lib/otp.ts` + the `request`/`confirm` routes reuse the exact pattern already built for `/api/verification/university/{request,confirm}`, just with a short numeric code (hashed at rest — unlike the long hex tokens elsewhere, an 8-digit code is meaningfully brute-forceable, hence `OTP_MAX_ATTEMPTS` + a ~20 min expiry) instead of a link.
- **Security tradeoff, resolved**: OTP possession alone (`otp_verified`) already lets the parent post a Request "for" the student — it does **not** wait for a further explicit student approval first. This was deliberate, not an oversight — see the long comment on `ParentStudentLink` in `prisma/schema.prisma` for the full reasoning (short version: nothing else a parent can do is gated by this link at all, so the actual risk at `otp_verified` is reputational/representation harm from a public post, not private data exposure — and blocking all on-behalf-of posting until an eventual, maybe-never-happens student signup would defeat the parent-first product goal). Required mitigations, not optional: (1) a distinct notice email to the student at link-creation time with a **no-account-required objection link** (`/family/link-objection` + `POST /api/family/link-objection/[token]/reject`) that immediately revokes; (2) that objection page requires an explicit button click before revoking, **never** auto-acts on page load/GET — email security scanners pre-fetch links (this bit us for real earlier in this project's own signup flow, see the OTP-vs-link section above) and an auto-revoking GET would let a scanner falsely kill a legitimate connection; (3) a revoked link cannot be silently re-established by the same parent re-running the OTP flow (`confirm/route.ts` checks for and rejects this).
- **Full account separation, always**: `ParentStudentLink` is a verification/relationship *fact*, never an access grant. A parent's `Request` always has `postedById = the parent's own User.id`; nothing about the link makes the student a `ConversationParticipant`, gives the parent message access, or merges the two accounts in any way, even after the student claims their record. Don't "helpfully" add implicit cross-visibility later — if a claimed student needs visibility into what's been posted for them, that's a filtered read of `Request` rows only, never a join into `Conversation`/`Message`.
- **`approved` status is now reachable** — `POST /api/family/link/[id]/approve` (the student's explicit upgrade from `otp_verified` to full trust) is implemented; see the Parent Link Approval section below. Still stubs: `src/app/api/family/invite/route.ts`/`invite/accept/route.ts`, the *other* direction (a student who already has an account invites a parent by email) — that direction should skip straight to `approved` on accept, not `otp_verified`, since the student's own initiating action is already unambiguous consent (asymmetric from the parent-initiated OTP flow on purpose).
- **Open, not yet decided**: how `Request` should reference a `StudentRecord` beneficiary — narrow replacement of the existing `beneficiaryId (User)` field, or an additive second nullable FK alongside it. The Trip Posting System (below) deliberately did **not** resolve this: every `Request` created there has `beneficiaryId = postedById` (self-authored only) specifically to avoid silently picking a resolution. On-behalf-of-student posting stays unbuilt until this fork is decided.

## Parent Link Approval

`POST /api/family/link/[id]/approve` is implemented — the student's explicit upgrade of an existing `ParentStudentLink` from `otp_verified` to `approved` described above. Caller must be `link.studentRecord.userId` (403 otherwise), and only an `otp_verified` link can be approved (400 for already-`approved` or `revoked`) — a guarded `updateMany` doubles as the concurrency check, same idiom used everywhere else in this codebase. **Deliberately does not wire a `VerificationRecord` on either user** — the original stub comment only hedged ("*consider*..."), and there's no student-side badge concept or UI slot anywhere to display one; the parent already got their `parent_relationship` badge back at `otp_verified` time (`parent-link/confirm/route.ts`), so nothing new is needed on that side either. Notifies the parent (`parent_link_approved` `NotificationType`, `relatedId` unused/null — no per-link page exists to deep-link to, so `notificationLink()` routes it to `/profile`, where the parent's own "Linked Students" section already shows current status for every link they have).

- **`/family`** (`src/app/family/page.tsx`, previously a bare, stale placeholder — its own copy contradicted the already-resolved "otp_verified can already post" decision) is now the **student's** view: lists every `ParentStudentLink` pointing at their own `StudentRecord`, each with an `ApproveLinkButton` (`src/components/ApproveLinkButton.tsx`, confirm()-gated same "can't be undone" framing as `MarkTripCompleteButton`) shown only on `otp_verified` rows. A parent visiting `/family` is pointed to `/profile` instead of duplicating the "Linked Students" list that already lives there. A user with no `StudentRecord` at all (alumni/traveler) sees a neutral explanatory message.

## Profile & Onboarding

Post-signup, both personas fill in a profile before (student) or as part of (parent) their first real use of the app.

- **Student** (`/onboarding`, reached by default right after signup verification — see `postConfirmPath` in `src/app/(auth)/sign-up/page.tsx`): name (prefilled from signup, editable), optional photo, home city (`User.homeCityId`, a `City` FK — supersedes the older unused `homeRegionId`), and optional enrichment fields (`major`, `year`, `travelPreferences` as free text, `lookingFor` as a `String[]` multi-select against `src/lib/lookingFor.ts`'s `LOOKING_FOR_OPTIONS`, which reuses the Post page's own four categories). University name and the verified badge are never entered here — always derived read-only from `VerificationRecord`/`StudentRecord`. This is a **soft nudge, not a hard gate**: `layout.tsx` shows a "Finish setting up your profile" banner (`hasCompletedOnboarding(user)` in `src/lib/auth.ts`, keyed on `User.onboardingCompletedAt`) but never blocks navigation on it — deliberately, to stay consistent with "routes are open, not gated" and avoid the redirect-chain complexity the parent gate already has.
- **Parent** (step 0 of `/family/connect-student`, ahead of the existing student-email/OTP steps — skipped automatically if `hasCompletedOnboarding(user)` is already true, e.g. when linking a second student later): name, optional photo, home city, phone (private — same visibility tier as email, never on the public profile), and `linkedStudentName` (free text, **self-declared by the parent**, not derived from the private `StudentRecord.fullName` — public, so another user can see who a parent is posting on behalf of). `linkedStudentName` is cleared server-side the moment the parent's last non-revoked `ParentStudentLink` is removed via the student's own objection link (`src/app/api/family/link-objection/[token]/reject/route.ts`) — it can never outlive its backing connection, since it names a third party (the student) who isn't the one publishing it.
- **Shared form**: `src/components/ProfileEditForm.tsx`, used by all three entry points above plus self-editing on `/profile`, gated by an `isParent` prop that decides which of the persona-specific fields render. All three submit to the single `PATCH /api/profile` (multipart/form-data — the same route also handles the optional photo upload). `onboardingCompletedAt` is set there, once, the first time it succeeds for a given user.
- **Verification badges shown alongside the profile**: `universityBadgeLabel(user)` (existing, student/alumni self-verified) and `parentRelationshipBadgeLabel(user)` (new — `VerificationRecord(type=parent_relationship)`, granted in `parent-link/confirm/route.ts` the moment a link OTP-confirms, revoked there in `reject/route.ts` under the same "last link removed" condition as `linkedStudentName`). A parent's own email is never expected to be university-verified, so `layout.tsx`'s "Verify your university email" nudge is suppressed entirely for `signedUpAsParent` accounts.
- **Public vs. private**: `src/lib/profile.ts`'s `getPublicProfile(userId)` is the single hand-picked `select` allowlist (deliberately never `include`) shared by both `GET /api/profile/[userId]` and the public `/profile/[userId]` page — public fields are name, photo, university, general home area, `major`/`year`/`travelPreferences`/`lookingFor`, `linkedStudentName`, and verification badges; private fields (email, phone, `StudentRecord` contents, `ParentStudentLink` rows, `signedUpAsParent`) never appear there. Viewing another user's public profile requires being logged in (no fully public/unauthenticated directory).
- **Photos**: Supabase Storage, bucket `avatars` (public-read, 5MB/JPEG-PNG-WebP limits — see `src/lib/supabase/storage.ts`). The bucket doesn't exist by default on a fresh Supabase project; create/configure it via `npm run supabase:setup-storage` (`scripts/setup-storage.ts`).
- **`User.collegeName`**: still unused/deprecated, as before — university affiliation is always derived from the verified `StudentRecord`/`VerificationRecord`, never this field.

## Trip Posting System

Built on the **existing** `Trip` (offers) and `Request` (rides or package needs, discriminated by `type`) models — not a new table. `/api/trips` and `/api/requests` (`POST`/`GET`, plus `/[id]` for `GET`/`PATCH`/DELETE-as-cancel) are implemented; `requests/[id]/{accept,decline,complete}` (matching a Request to a Trip) are now implemented too — see the Request/Trip Matching Lifecycle section below — but were built as a separate, later effort from posting itself. `conversations` (messaging) is also implemented, see the Messaging section below — it's a distinct effort from matching, not a prerequisite for it.

- **Entry point**: `/post` links to two forms, not four, even though it shows four labeled actions — "Offer a Ride" and "Offer Package Space" both create a `Trip` (they're attributes of the same journey: `seatsTotal`/`seatsRemaining` for riders, `packageSpaceAvailable`/`packageCapacityNote` for packages, live on the same row); "Need a Ride" and "Need Something Delivered" both create a `Request` with `type` pre-selected via a query param. Forms: `src/components/TripPostForm.tsx`, `src/components/RequestPostForm.tsx` — both used for create (`POST`) and edit (`PATCH`), same convention as `ProfileEditForm` (full-state submission, not partial patches). Shared Zod schemas live in `src/lib/postSchemas.ts`, not inside the route files themselves — Next.js's route export validation rejects any named export from a `route.ts` that isn't a recognized HTTP method or route config key, so a schema can't be exported directly from a route handler and imported elsewhere.
- **Standalone only**: every `Request` created here has `tripId = null` (the "requester posts first" flow) — "request against a specific existing Trip" is a matching concept, deliberately not built.
- **Ownership**: enforced in application code (this project has no Postgres RLS anywhere — Prisma connects directly, bypassing it), the same pattern as the rest of the app — `getCurrentUser()` first, then an explicit `travelerId`/`postedById` comparison against the caller on every `PATCH`/DELETE. A `Request`'s owner for editing purposes is `postedById` (who posted it), not `beneficiaryId` (who it's for) — today these are always the same person, see the on-behalf-of-student note above.
- **Delete is a soft cancel** (`status → cancelled`), not a row removal — consistent with how every other lifecycle in this schema already works via a status enum, and avoids FK issues once `Conversation`/accepted-`Request` rows can reference a `Trip`.
- **Pages**: `/post/trip` and `/post/request` (create), `/my-posts` (lists the caller's own Trips and Requests, split into Upcoming/History tabs via `?tab=history`; Requests use a purely date-based split — `Request.neededDate` vs. "now", independent of status, same as originally built — while Trips now bucket by `tripDisplayStatus` instead, see the Trip Management section below for why that changed), `/trips/[id]` and `/requests/[id]` (detail, Edit/Cancel shown only to the owner), `/trips/[id]/edit` and `/requests/[id]/edit`.
- **Two small schema additions** beyond what `Trip`/`Request` already had: `flexibleTime` (`Boolean`, both models) and `neededTime`/`notes` (`Request`, mirroring `Trip.departureTime`/`tripNotes`) — purely descriptive, no matching/search logic reads them yet.
- **Past-due status is derived, never persisted**: `src/lib/postStatus.ts`'s `tripDisplayStatus`/`requestDisplayStatus` compute an "expired" display state at read time for a non-terminal post (`upcoming`/`pending`/`accepted`) whose date has passed, without writing to the DB `status` column — same pattern as `getPrimaryRouteLabel()` in `geo.ts`. Deliberately not `completed`: that status specifically means the trip/request was matched and finished (it's what gates `Review` creation), so reusing it for "the date just passed" would be wrong.
- **`Trip.title`**: a required (at the Zod layer; nullable in the DB since it postdates this model's earliest rows) short subject line stating the purpose of the post, shown as the page heading on `/trips/[id]` and in the `/my-posts` list. `Request` has no equivalent field.
- **Write-in destination**: `Trip.destinationCityId`/`Request.destinationCityId` are both nullable, paired with a new `destinationText String?` on each model — a poster can pick a listed `City` or type a destination that isn't seeded (e.g. an airport), never both. `tripFieldsSchema`/`requestFieldsSchema` (`src/lib/postSchemas.ts`) enforce "exactly one of the two" via `.refine()`, not a DB constraint. `TripPostForm`/`RequestPostForm` implement this as a `<select>` with a sentinel `"Other (type it in)"` option that reveals a free-text input. Origin stays City-only on both models — this only applies to the destination side.

## Home Page

`/` (`src/app/page.tsx`) is the narrow "surfaces the featured corridor prominently" glance view the plan doc describes — `RouteCommunity.active` controls what Home features by default, while Explore/search (below) surfaces trips across any city pair. Reuses Explore's exact Trip/Request query shape (ride-only, own posts and blocked users excluded, `tripDisplayStatus`/`requestDisplayStatus` filtering, the batched `ConnectionRequest`-status lookup, `ExploreCard`/`PosterBadge` rendering) with one addition: a region-pair scope filter, and no filter form or pagination — Home is meant to be glanced at, not searched; `/explore` is linked out to for that. This closes the last real functional gap in the app (per CLAUDE.md's own accounting) — `/` was previously the only page with no login gate and no data at all, a pure placeholder.

- **`getFeaturedRoutePairs(user)`** (`src/lib/geo.ts`) resolves what region pair(s) to scope the feed to, returning `{ pairs: FeaturedRoutePair[], isPersonal: boolean }`. Tries the user's *personal* route first — the exact same derivation `getPrimaryRouteLabel` already uses (home region vs. university region, matched against an existing `RouteCommunity` row in either order) — and falls back to every currently-`active` `RouteCommunity` row (plural-safe: the schema has no constraint limiting "at most one active," even though seed data has exactly one) if no personal route is derivable (a parent, an alumni, or a student whose region pair has no `RouteCommunity` row at all). This is the **first code anywhere that actually reads `RouteCommunity.active`** — `getPrimaryRouteLabel` itself never checked it, since a personal route is valid regardless of whether its RouteCommunity happens to be flagged active or not. The two functions' personal-route condition deliberately stays duplicated rather than sharing a helper (different return shapes: a label string vs. queryable region ids+names) — each has a comment cross-referencing the other so they can't silently drift apart, since `/profile`'s displayed label and Home's actual feed scope must never visibly disagree for the same user.
- **Query scoping**: an `OR`-of-both-directions filter (`originCity: { regionId: A }, destinationCity: { regionId: B }` or vice versa, flatMapped across every pair in scope) ANDs into Explore's existing `status`/`travelerId`/`postedById`/blocked-ids conditions — a cross-region match, not "touches this region at all," matching the "Bay Area ↔ UCI corridor" framing precisely. If no pairs resolve at all (no personal route, no active `RouteCommunity`), Home skips the Trip/Request queries entirely and shows a generic empty state rather than querying with no filter.
- **Heading** reflects which branch resolved: "Your route: X ↔ Y" when personal (identical label shape to `/profile`'s own `getPrimaryRouteLabel` string), "Featured route: X ↔ Y" when falling back to the active community.
- **Ride-only**, same "package browsing is separate, out of scope" precedent Explore already set (see below) — not an oversight, and not new scope invented for Home.
- **Auth-gated** (`getCurrentUser()` → `redirect("/login")`), matching every other authenticated page — previously the only page in the app without this check, which was a gap rather than a deliberate logged-out-marketing-page design (nothing else in this app has that concept).

## Explore Page

`/explore` (`src/app/explore/page.tsx`) browses upcoming Trip (offer) and standalone ride Request (need) posts from **other** users, merged into one feed — a server component querying Prisma directly, same convention as `/my-posts` and the Trip/Request detail pages, not a client-side fetch against `/api/trips`/`/api/requests`.

- **Scope: rides only.** Every card field the requirements call for (origin/destination/date/time/seats/offer-vs-request) is ride-shaped, so this merges `Trip` (all of them are ride offers) with standalone (`tripId = null`) `Request` rows where `type = "ride"` only — package requests aren't browsable here. This is a deliberate scope decision, not an oversight; package browsing would need its own card shape.
- **Excludes the caller's own posts**: `travelerId: { not: user.id }` / `postedById: { not: user.id }`, mirroring the ownership pattern `/my-posts` and the detail pages already use for edit/cancel permission checks.
- **Excludes anything not currently actionable**: DB-level `status: "upcoming"` (Trip) / `status: "pending"` (Request), further filtered in application code through `tripDisplayStatus`/`requestDisplayStatus` (`src/lib/postStatus.ts`) so a past-due post that never got cancelled doesn't show as if it were still open — same derived-at-read-time helpers `/my-posts` uses, nothing new persisted.
- **Filters** (`originCityId`, `destinationCityId`, `date`, `kind`) are plain `<form method="get">` query params, not client state — submitting does a normal navigation to `/explore?...`, re-running the server component, the same zero-JS pattern as the Upcoming/History tabs on `/my-posts`. `getCitiesByRegion()` (`src/lib/geo.ts`) populates the origin/destination pickers.
- **Loading/error states use Next.js App Router file conventions** (`src/app/explore/loading.tsx`, `src/app/explore/error.tsx`) rather than component-level state — the first file convention of this kind in the project; reach for the same pattern before inventing a bespoke spinner/error boundary elsewhere.
- **`src/components/ExploreCard.tsx`** renders one card from a normalized `TripCardPost | RequestCardPost` union built in the page. The poster's Student/Parent status label is computed locally in that file from a minimal `{ signedUpAsParent, verifications }` shape selected directly on the query — **not** `universityBadgeLabel`/`parentRelationshipBadgeLabel` from `src/lib/auth.ts`, which require the full `CurrentUser` include shape (`parentLinksAsParent`, `homeCity`, `studentRecord`, …) that browsing another user's post has no reason to fetch.

## Messaging

Implements the `Conversation`/`Message` module the plan doc (§11) describes: "a prospective requester can message the traveler with questions *before* committing to a formal request" — `Conversation` stays scoped to `(tripId, counterpart)`, `requestId` stays null (no UI sets it yet). This module itself deliberately does **not** create a `Request` or touch `Trip.seatsRemaining` directly — don't let "register for a seat" as a button label imply a real reservation exists yet. (The request/trip matching lifecycle and Seat Offers, both now implemented — see their own sections below — are separate mechanisms that *do* eventually touch `seatsRemaining`; Seat Offers in particular is reached from within a `Conversation` created by this module, but the two remain distinct systems.)

- **Entry point**: `RegisterInterestForm` (`src/components/RegisterInterestForm.tsx`) on `/trips/[id]`, shown to non-owner viewers only when the trip is actionable (`tripDisplayStatus(trip) === "upcoming"`) and `seatsRemaining > 0`. Clicking "Register for a seat" reveals a message composer (prefilled, editable) rather than firing silently — the button *prompts* a message, it doesn't send a canned one unseen.
- **`POST /api/conversations`** (`src/app/api/conversations/route.ts`, previously nonexistent — the API module listing below only had `[id]/messages`) takes `{ tripId, body }`, finds-or-creates a `Conversation` for `(tripId, caller, trip.travelerId)`, and creates `body` as the first `Message`. Rejects messaging your own trip and messaging a non-upcoming trip (`tripDisplayStatus(trip) !== "upcoming"`) server-side, not just via the UI gate above. The find-or-create is a plain find-then-create, **not** the race-hardened pattern `claimOrCreateStudentRecord` uses for `StudentRecord` — a duplicate thread here is a minor UX nuisance, not a security or data-integrity issue, so that extra rigor isn't worth it here.
- **`GET /api/conversations`** lists the caller's threads (most recent first) for `/messages`; **`GET /api/conversations/[id]`** and **`GET`/`POST /api/conversations/[id]/messages`** (the latter two previously `501` stubs, now implemented) all 404 — not 403 — when the caller isn't a `ConversationParticipant`, so a thread's existence isn't leaked to someone outside it. The participant check is a small local (non-exported) helper duplicated across these files rather than pulled into a shared lib module — each file's route export validation only allows HTTP-method exports, and the check is a few lines, not worth a new module for.
- **Polling, not websockets/realtime** (plan doc §14): `MessageThread` (`src/components/MessageThread.tsx`), the client component behind `/messages/[id]`, re-fetches `GET .../messages?since=<lastMessageTimestamp>` every 4s while the thread is mounted. `since` is always a pre-serialized ISO string on both the initial server-rendered messages and every polled batch, so the component's `Message` type never has to reconcile a `Date` object from one path against a JSON string from the other.
- **No rate limiting or spam controls on messages** — the existing `canCreatePost` limiter (`src/lib/rate-limit.ts`) only applies to Trip/Request creation. Out of scope for this pass; revisit if messaging abuse becomes a real problem.
- **Unread indicators**: `ConversationParticipant.lastReadAt` (nullable `DateTime`, migration `20260819021514_add_conversation_participant_last_read_at`) records when each participant last opened a thread. `src/lib/messaging.ts`'s `isConversationUnread` is the single unread rule (latest message from the other party, and either never-opened or that message postdates `lastReadAt`) — shared by `/messages` (bold title + "New" badge per row) and the nav's "Messages" item (`src/app/layout.tsx`, red count badge via `getUnreadConversationCount`, also in `src/lib/messaging.ts`). `MessageThread` calls **`POST /api/conversations/[id]/read`** on mount and after every poll that brings in new messages, so opening a thread — or leaving it open while a reply arrives — keeps it marked read. That route's `updateMany` on `(conversationId, userId)` doubles as its own authorization check (0 rows updated → 404), the same "don't leak conversation existence" pattern as the other `/api/conversations/[id]*` routes.
- **`findOrCreateConversationForTrip(tripId, userIdA, userIdB)`** (`src/lib/messaging.ts`) is the one conversation-creation code path in the app — extracted from `POST /api/conversations` so `POST /api/connection-requests/[id]/accept` (see Connection Requests below) can reuse it exactly rather than standing up a second way to create a `Conversation`.
- **Archive/Delete + last-activity timestamp** (migration `20260828172647_add_conversation_archive_delete`): `/messages` now shows each row's last-activity time (`lastMessage?.sentAt ?? conversation.createdAt`, same `.message-meta` timestamp styling used inside the thread) and a per-row `ConversationActions` control (`src/components/ConversationActions.tsx`). Both new fields live on `ConversationParticipant`, not `Conversation` — this is a **per-user view preference**, never a shared/destructive action: one participant hiding a thread never touches the Conversation/Message rows themselves or the other participant's own view, same "don't delete shared history" precedent as Trip cancellation leaving `ConnectionRequest`/`Conversation` rows untouched.
  - **`archivedAt`**: `POST /api/conversations/[id]/archive` / `.../unarchive`. Sticky — a new message does **not** auto-clear it, the user has to explicitly unarchive. `/messages` gets an Inbox/Archived `?tab=` split (same zero-JS query-param convention as `/my-posts`/`/connections`); `getUnreadConversationCount` (nav badge) excludes archived conversations, since the badge's purpose is prompting a check of the main inbox.
  - **`deletedAt`**: `DELETE /api/conversations/[id]` (confirm()-gated in the UI). Hides the thread from **both** tabs entirely — there's no separate "trash" view. Unlike `archivedAt`, this **is** auto-cleared the moment either party sends a new message, so a deleted thread resurfaces on new activity instead of silently going unnoticed forever: `findOrCreateConversationForTrip` clears it when *reusing* an existing conversation (covers the "connect again after accepting/registering interest" path, since both of its callers create their own first `Message` directly rather than going through the messages route), and `POST /api/conversations/[id]/messages` clears it independently for the ongoing-chat case that never calls `findOrCreateConversationForTrip` at all. Both routes use the same `updateMany`-as-authz idiom as `POST /api/conversations/[id]/read`.

## Connection Requests

A formal, gated request-to-connect lifecycle (`ConnectionRequest` model: `pending` → `accepted`/`declined`/`cancelled`) layered **on top of**, not instead of, the ungated Messaging flow above — RegisterInterestForm's "message the traveler immediately, no approval needed" behavior is untouched. The two are genuinely different products: RegisterInterestForm is "ask a quick question," ConnectionRequest is "ask the trip owner's explicit permission before a thread exists." Both end up at the exact same place once a connection exists — a `Conversation` via `findOrCreateConversationForTrip` — so accepting a `ConnectionRequest` and clicking "Register for a seat" on the same trip pair converge onto one thread, not two.

- **Where the button lives**: `ConnectionRequestButton` (`src/components/ConnectionRequestButton.tsx`) appears in two places for the same reason RegisterInterestForm only appears once — non-owner viewers of an *upcoming* trip: `/trips/[id]` (via a server-fetched `myConnectionRequest`/`acceptedConversation` lookup) and every offer `ExploreCard` (via a single batched query in `/explore/page.tsx`, not one query per card). The button only reflects whether there's a **live** (pending/accepted) request — a declined or cancelled one reverts it to a plain, clickable "Request to Connect" again, since only a *pending* duplicate is blocked (see the schema comment on `ConnectionRequest`). The historical declined/cancelled record is what `/connections`'s Sent tab is for, not this button.
- **`ExploreCard` restructuring**: the card is now a `<div>` wrapping an inner `<Link>` (renamed `.explore-card-link`) plus a sibling `.explore-card-actions` region for the button — previously the whole card *was* the `<Link>`. This was a required, not cosmetic, change: HTML disallows interactive content (a `<button>`) inside an `<a>`, and nesting them would make clicks ambiguous anyway. `PosterBadge` (the avatar/name/role block) is now exported from this file and reused by `/connections` for "Requester's name, Profile picture, Student/parent status" rather than re-implementing that block a third time.
- **`POST /api/connection-requests`** (body `{ tripId }`) always derives `requesterId` from the authenticated caller and `recipientId` from `trip.travelerId` — neither is ever read from the request body, which is what actually prevents "create a request pretending to be someone else," not a check that could be bypassed. Rejects your own trip, a non-upcoming trip (same `tripDisplayStatus` gate `POST /api/conversations` uses), and a duplicate *pending* request (409) via a plain find-then-create — same "minor UX nuisance, not worth race-hardening" calibration as `findOrCreateConversationForTrip`.
- **`POST /api/connection-requests/[id]/{accept,decline,cancel}`**: accept/decline require `recipientId === caller` (403 otherwise); cancel requires `requesterId === caller` (403 otherwise) — the inverse ownership check on purpose, since only the requester should be able to withdraw their own ask. All three require `status === "pending"` first (400 "already resolved" otherwise) — there is no un-declining or re-accepting a resolved request. These three use 403 for a wrong-caller mismatch, not the 404-to-avoid-leaking-existence pattern the private `Conversation` thread routes use — `ConnectionRequest` ownership checks are conceptually closer to the existing `Trip`/`Request` ownership checks (which are already 403 elsewhere in this codebase) than to a DM thread's privacy model. Only `accept` touches `Conversation`, via `findOrCreateConversationForTrip`; `decline` and `cancel` never create one.
- **`/connections`** (Received default, `?tab=sent`) follows the exact `/my-posts` Upcoming/History convention — plain query param, server-rendered, no client JS for the tab switch. Pending rows get `RespondToConnectionRequestButtons` (Accept/Decline, Received tab only) or `CancelConnectionRequestButton` (Sent tab only). Decline and Cancel follow `DeletePostButton`'s confirm-then-fetch-then-`router.refresh()` shape; **Accept does not** — it `router.push()`es straight to `/messages/[conversationId]` (the id `POST .../accept` already returns) instead of staying on `/connections`, since the whole point of accepting is to land in the resulting chat.
- **No DB-level uniqueness on `(tripId, requesterId)`** — see the long comment on the `ConnectionRequest` model in `prisma/schema.prisma` before adding one; a blanket unique constraint would block the intentional "try again after a decline" flow.
- **Required note (`ConnectionRequest.message`, migration `20260820170907_add_connection_request_message`)**: clicking "Request to Connect" reveals a composer (`ConnectionRequestButton`'s `composing` state) with a **required** textarea, labeled "Tell the trip owner why you're connecting" — same reveal-on-click shape as `RegisterInterestForm`, but a plain one-click request with no context is no longer possible; both the client (`disabled={loading || !message.trim()}`) and `POST /api/connection-requests` (Zod `.min(1, ...)`) enforce this, the DB column itself stays nullable only because it postdates this model's earliest rows (same convention as `Trip.title`). `POST /api/connection-requests` folds a truncated preview into the `connection_request` notification text. `/connections` renders it (both tabs) as an italicized `.connection-item-message` line under the status, so the trip owner has context *before* deciding — this is the primary point of the field. If the request is later accepted, `POST /api/connection-requests/[id]/accept` seeds the same text as the first `Message` in the resulting `Conversation` (sender = the requester), so the context carries into the chat too rather than being stranded on a row the requester can no longer act on.

## Notifications

An in-app `Notification` model (`prisma/schema.prisma`), one row per event, read by the caller only — no push/email/SMS delivery. `src/lib/notifications.ts`'s `createNotification()` is the single creation path (same "one function, every trigger site calls it" convention as `findOrCreateConversationForTrip`), called from exactly four places today: `POST /api/connection-requests` (notifies the trip owner), `POST /api/connection-requests/[id]/accept` and `.../decline` (both notify the original requester), and the two message-creation routes (`POST /api/conversations` and `POST /api/conversations/[id]/messages`, both notify the other conversation participant(s), never the sender). Each of those events is naturally non-duplicating: connection-request creation is already blocked from duplicating by the existing pending-request check, accept/decline can each only fire once per request (`status !== "pending"` guard), and a message notification corresponds 1:1 with an actual new `Message` row.

- **Fields**: `type` (`connection_request` | `connection_accepted` | `connection_declined` | `new_message`), `title`, `message` (both plain strings written at creation time, not re-derived at read time — a notification still reads correctly even after the thing it points at changes state further), `relatedId` (untyped, points at whichever entity `type` implies — a `ConnectionRequest` or a `Conversation`, never a second FK per possible target), `isRead`, `createdAt`.
- **Where a click goes**: `notificationLink()` (`src/lib/notifications.ts`) is the one type→URL mapping. `connection_request` → `/connections` (Received tab, the default); `connection_declined` → `/connections?tab=sent`; `connection_accepted`/`new_message` → `/messages/[relatedId]` (the conversation thread). The first two don't deep-link to a single row because a connection request can be re-sent after a decline, so there's no permanently stable target to point at.
- **`/notifications`**: a server component querying Prisma directly (same convention as `/messages`/`/connections`, not a client fetch against a GET listing route — there is no `GET /api/notifications`), most recent first, capped at 100 rows (a simple cap, not real pagination, consistent with the rest of the app). Has `loading.tsx`/`error.tsx` following the Explore page's App Router file-convention pattern. Each row is `NotificationItem` (`src/components/NotificationItem.tsx`, client component): the whole row is a `Link` to `notificationLink()`'s target, and clicking it fires a fire-and-forget `POST /api/notifications/[id]/read` (same pattern `MessageThread` uses for its own read receipts) before letting navigation proceed — no `preventDefault`, so Next's `Link` still navigates normally. A separate small "Mark as read" button covers marking a notification read without leaving the page. `MarkAllNotificationsReadButton` posts to `POST /api/notifications/read-all`.
- **Security**: `POST /api/notifications/[id]/read` uses the same `updateMany(WHERE id, userId)`-doubles-as-authorization pattern as `POST /api/conversations/[id]/read` — 0 rows affected (wrong owner or nonexistent id) returns a 404, no distinction leaked. `POST /api/notifications/read-all` scopes its `updateMany` to `WHERE userId = caller`, so it can only ever touch the caller's own rows — there's no id parameter for another user's id to leak into.
- **Nav bell**: `layout.tsx` adds a "🔔 Alerts" item to `NAV_ITEMS`, badge-count computed via `getUnreadNotificationCount()` (`src/lib/notifications.ts`) the same way the existing "Messages" badge already works — computed fresh on every full server render, not client-polled. Deliberately a separate count from the Messages unread-conversation count, not merged into one total: an accepted/declined connection request has no corresponding "unread conversation" at all, so folding them together would either double-count message notifications or silently drop connection-request ones from the badge. Like the Messages badge, this only recomputes on a full page load/server render — a client-side `<Link>` navigation that stays under the same root layout won't refresh it immediately, the same already-documented Next.js App Router caveat noted under Auth Architecture for the parent-link gate.

## Trip Management (Trip Lifecycle)

A `Trip` now moves through a real three-stage lifecycle -- `upcoming` → `completed` | `cancelled` -- with the owner-facing actions (Edit, Cancel, Mark Completed) that make those transitions reachable. This is deliberately scoped to `Trip` only, not `Request` -- a standalone Request's own owner-driven "mark completed" step is still unbuilt (`requests/[id]/complete` remains a `501` stub), a separate, not-yet-decided piece of work.

- **`TripStatus.active` was renamed to `upcoming`** (migration `20260820051301_trip_lifecycle_and_cancel_notification`, a real Postgres `ALTER TYPE ... RENAME VALUE` -- a metadata-only change, so the two rows that already existed under `active` came along automatically with no data rewrite and no need to backfill). Every prior `status: "active"` / `tripDisplayStatus(trip) === "active"` comparison in the codebase (Explore's query, `POST /api/trips`, `POST /api/connection-requests`, `POST /api/conversations`, the trip detail page, `postStatus.ts`) was updated to `"upcoming"` in the same pass. Do this kind of rename sparingly -- it was judged worth it here specifically because the mismatch between "active" (implies presently happening) and what the value actually means (not yet departed, still actionable) was a real, recurring point of confusion once a genuine 3-stage lifecycle existed to name precisely, and the blast radius was small (six call sites) and mechanically safe (`RENAME VALUE`, not a drop-and-recreate).
- **Edit** (`PATCH /api/trips/[id]`, `/trips/[id]/edit`): only reachable while `trip.status === "upcoming"` -- enforced in the route (400 otherwise) and in the edit page itself (redirects back to the detail page for a non-upcoming trip), not just by hiding the Edit link. No clear product reason surfaced for allowing edits on a completed/cancelled trip, so it's fully blocked rather than half-allowed.
- **Cancel** (`DELETE /api/trips/[id]`, `DeletePostButton` with trip-specific `actionLabel`/`confirmMessage` props): only reachable from `upcoming`. Confirmation is the existing `confirm()` dialog `DeletePostButton` already used for Request cancel, just with trip-specific copy that mentions connected users get notified. Cancelling:
  1. Sets `Trip.status = "cancelled"` and, in the same `$transaction`, bulk-flips every **pending** `ConnectionRequest` on that trip to `status = "cancelled"` too -- reusing the existing status value a requester's own `/cancel` already produces (from the requester's side, "my request is cancelled" reads correctly regardless of who triggered it), rather than inventing a new `ConnectionRequestStatus`.
  2. Leaves every **accepted** `ConnectionRequest` completely untouched -- status stays `accepted`, its `Conversation` stays fully intact and browsable. Per product decision, cancelling the trip never deletes or hides historical connection data.
  3. Notifies every affected requester (pending or accepted) via the one notification path (`createNotification`, see Notifications above) with a new `trip_cancelled` `NotificationType` -- wording differs by case ("your request has been cancelled" vs. "your conversation is still available"), but both link to `/connections?tab=sent` (`notificationLink()` in `src/lib/notifications.ts`), since that tab already shows the right status and links into the trip either way.
- **Mark Completed** (`POST /api/trips/[id]/complete`, `MarkTripCompleteButton.tsx`): only reachable from `upcoming`, owner-only, `confirm()`-gated. A distinct, simpler thing from the still-unimplemented `POST /api/requests/[id]/complete` stub -- that one is the Request/Trip *matching* lifecycle's completion step (gated on both participants, unbuilt); this is just the owner declaring their own Trip done, no counterpart negotiation. Deliberately does **not** touch any `ConnectionRequest` on the trip -- per product decision, existing connections (pending or accepted) remain exactly as they were, "available for future features such as ratings/reviews." The one thing that does change as a result: `POST /api/connection-requests/[id]/accept` now re-checks `tripDisplayStatus(connectionRequest.trip) === "upcoming"` before accepting (400 otherwise) -- this is what actually prevents a stale pending request from being accepted against a trip that's already completed (or cancelled, though a cancelled trip's pending requests are already flipped away from `"pending"` by step 1 above, so this check mostly matters for the completed case).
- **Trip detail page (`/trips/[id]`)**: owner actions (Edit · Mark Completed · Cancel Trip) show only while `isUpcoming`. For non-owners, an **already-accepted** connection keeps showing its "Connected — View messages" state even after the trip stops being upcoming (`connectionRequestStatus === "accepted" || isUpcoming` gates the `ConnectionRequestButton`) -- only a *fresh* request is blocked once the trip isn't upcoming, not the visibility of an existing one. A non-owner with no accepted connection sees a plain "This trip is no longer accepting connections." message instead of the request/register-interest controls silently vanishing.
- **`/my-posts`**: the Upcoming/History *tabs* are unchanged (still the same nav, still date-independent for Requests), but what counts as "Upcoming" for **Trips** changed from a pure date split to `tripDisplayStatus(trip) === "upcoming"` -- a cancelled-but-future-dated trip used to sit under Upcoming with just an inline "(cancelled)" label, which is exactly the muddled experience this feature was asked to fix. The History tab now sub-groups Trips under **Completed**, **Cancelled**, and (only if any exist) **Past due** headings — the last one covers a trip whose DB status is still `upcoming` but whose date has passed without the owner marking it completed or cancelled (`tripDisplayStatus` returns `"expired"` for these); Past-due trips still show the full Edit/Mark Completed/Cancel action row (nudging the owner to resolve them), since they're still `status: "upcoming"` under the hood. Each Trip row also shows a cheap connection-request summary ("3 connection requests (1 accepted)"), computed via one `groupBy` query across all the caller's trips rather than per-row — this is what satisfies "show relevant trip and connection information" for Completed trips without building any new feature.
- **Explore integration required no new filtering logic** — `/explore` and `GET /api/trips` already filtered on `status: "upcoming"` (formerly `"active"`) at the DB level plus `tripDisplayStatus(trip) === "upcoming"` in application code; once Cancel/Complete can actually change a Trip's status, those existing filters do the rest. Same for the "prevent new connection requests to an inactive trip" requirement — `POST /api/connection-requests` and `POST /api/conversations` already rejected a non-upcoming trip server-side from when Explore was first built.
- **Security**: every new/changed route (`PATCH`, `DELETE`, `POST .../complete` on `/api/trips/[id]`) follows the exact existing pattern — `getCurrentUser()`, then `trip.travelerId !== user.id` → 403, then a `trip.status !== "upcoming"` check → 400 — enforced server-side regardless of what the UI shows or hides. There is still no Postgres RLS in this project; these checks are the only enforcement, same as everywhere else (see Trip Posting System above).

## Trip Participants (Seat Confirmation)

Lets a Trip owner turn an accepted `ConnectionRequest` into an actual confirmed seat, decrementing `Trip.seatsRemaining` — the first real write path for that field other than the create/edit "reset to seatsTotal" paths (see Trip Posting System above). This is deliberately built on `ConnectionRequest`, **not** the standalone Request/Trip matching lifecycle (`requests/[id]/accept` — see the Request/Trip Matching Lifecycle section below, now implemented) — those are two different products solving similar-sounding problems: matching lets a *standalone* `Request` (posted independently, `tripId = null`) get attached to a `Trip` by the trip owner accepting it, and draws from this exact same `seatsRemaining` pool, but doesn't touch `ConnectionRequest` at all. Seat confirmation instead answers a narrower question — "of the people I'm already connected with about this specific trip, who's actually riding" — using data that already exists (everyone here went through Request to Connect → Accept first) and needing no new "search for a user to add" surface, which this app deliberately doesn't have (no public user directory, see Profile & Onboarding above).

- **Schema**: `ConnectionRequest.seatConfirmedAt` (nullable `DateTime`, migration `20260820215259_trip_participants_seat_confirmation`) is set/cleared only ever inside the same DB transaction as an opposite decrement/increment of `Trip.seatsRemaining` — the two fields have no other way to stay in sync, since `seatsRemaining` doesn't otherwise derive from anything. Distinct from `status` itself: not every accepted connection becomes a rider (a chat that fell through, or a package-only connection), so `status = accepted` alone doesn't imply a seat is held.
- **`POST /api/connection-requests/[id]/confirm-seat`**: owner-only (`recipientId === caller`, 403 otherwise), requires `status === "accepted"` and `seatConfirmedAt` still null (400 otherwise), and requires `tripDisplayStatus(trip) === "upcoming"` (400 otherwise — same gate `accept`/`POST /api/conversations` already use). The capacity check and decrement run inside one interactive `$transaction`: `Trip.seatsRemaining` is decremented via an `updateMany` guarded on `seatsRemaining: { gt: 0 }` (the same "0 rows affected" idiom already used for `POST /api/conversations/[id]/read` and `POST /api/notifications/[id]/read`, here repurposed as a concurrency guard rather than an authorization check) — if that affects zero rows, the whole transaction throws and nothing is written, including `ConnectionRequest.seatConfirmedAt`. This is exactly the "capacity check + decrement inside a single DB transaction to prevent overbooking races" the old `requests/[id]/accept` `TODO` comment called for, just applied to this narrower feature. On success, notifies the requester (`trip_seat_confirmed` `NotificationType`, links to `/trips/[id]` via `notificationLink()` — the only notification type whose `relatedId` is the trip's own id rather than a `ConnectionRequest`/`Conversation` id, since the rider's own status is already visible right there on the trip detail page).
- **`POST /api/connection-requests/[id]/release-seat`**: owner-only, requires `seatConfirmedAt` already set (400 otherwise). Undoes a confirm-seat mistake — clears `seatConfirmedAt` and increments `seatsRemaining` back, in one transaction. Deliberately has **no** upcoming-only restriction (unlike confirm-seat) and sends **no** notification — this is a correction of the owner's own bookkeeping, not a new user-facing event, same product judgment as Mark Completed not touching `ConnectionRequest` at all.
- **Trip detail page (`/trips/[id]`)**: owners see a "Participants" section listing every accepted `ConnectionRequest` **and** every accepted `SeatOffer` for the trip (see Seat Offers below — the two mechanisms are merged into one roster, since from the owner's point of view it's just "who's riding"), `PosterBadge`-rendered (reused from Explore/`/connections`), each with `ConfirmSeatButton` (`src/components/ConfirmSeatButton.tsx` — generalized via an `id`/`kind` prop pair rather than a `ConnectionRequest`-specific one, toggles between "Add as Participant" and "✓ Confirmed · Remove", same confirm-then-fetch-then-`router.refresh()` shape as `MarkTripCompleteButton`, `confirm()`-gated only on the Remove path; a `SeatOffer` row is only ever rendered already-confirmed, so "Add as Participant" is unreachable for that kind). Shown regardless of trip status, not just `isUpcoming`, so a completed/cancelled trip's participant history stays visible and correctable — only "Add as Participant" itself is upcoming-gated (disabled once `seatsRemaining` hits 0, hidden entirely once the trip isn't upcoming and the connection was never confirmed, since confirm-seat would 400 either way). A confirmed rider sees their own "✓ You have a confirmed seat on this trip." note next to their `ConnectionRequestButton` — `RegisterInterestForm`'s "Register for a seat" button (the ungated ask-a-question flow, see Messaging above) still shows alongside it whenever seats remain, since the two flows remain genuinely independent.
- **Trip edit (`PATCH /api/trips/[id]`) had to change**: it used to unconditionally reset `seatsRemaining` to the new `seatsTotal`, correct only because "nothing can have booked a seat yet" — no longer true once this feature exists. It now computes a consumed-seats total via `getConfirmedRiderCounts` (`src/lib/tripParticipants.ts` — `ConnectionRequest.seatConfirmedAt` + `SeatOffer.seatConfirmedAt`, **plus** accepted-Request seats summed separately — every mechanism that can hold a seat, see the Request/Trip Matching Lifecycle and Seat Offers sections) and sets `seatsRemaining = seatsTotal - totalConsumed`, rejecting the edit outright (400, not silently clamped) if the new `seatsTotal` would go below the already-consumed total — there's no correct number to fall back to in that case; the owner has to release a seat first.
- **Security**: both new routes follow the exact existing `getCurrentUser()` → ownership check (403) → status check (400) pattern used everywhere else in this file; no Postgres RLS, same as always.
- **Confirmed riders are public, not owner-only** (per product decision): `/trips/[id]` shows a read-only "Riders" section to **non-owner** viewers listing everyone with a confirmed seat (`confirmedRiders`, the `seatConfirmedAt`-filtered subset of the owner's own `participantRows` — deliberately narrower than what the owner sees, since the owner's full list also includes accepted-but-not-yet-confirmed `ConnectionRequest` candidates, an in-progress management detail that stays private). No management buttons on this public view, just `PosterBadge` per rider. The same count also surfaces compactly on `/explore` and Home cards via `ExploreCardPost.confirmedRiderCount` ("🎫 N confirmed riders", shown only when `> 0`) — computed batched across every card via `getConfirmedRiderCounts(tripIds)` (`src/lib/tripParticipants.ts`, the same helper `PATCH /api/trips/[id]` uses for its own single-trip count), so browsing either page never does a per-card query.

## Seat Offers

The owner-initiated counterpart to Trip Participants above: a trip owner can offer a seat directly to someone they're already messaging (e.g. via `RegisterInterestForm`'s ungated "Register for a seat" DM), not just people who've gone through the requester-initiated Request to Connect flow. Before this, someone who only DMed the owner had no path at all into the Participants roster — that list only ever pulled from accepted `ConnectionRequest`s.

- **`SeatOffer` model** (migrations `20260828165939_add_seat_offers` + `20260828170524_add_seat_offer_trip_cancelled_notification_type`): `tripId`, `recipientId`, `conversationId` (always sent from within an existing `Conversation` — there's no other UI surface to reach this from), `status` (`pending → accepted/declined/cancelled`), `seatConfirmedAt` (kept separate from `status`, same convention as `ConnectionRequest.seatConfirmedAt`, so a later "Remove" doesn't erase the historical fact that the recipient accepted). Deliberately **not** built by reusing `ConnectionRequest` with a reversed direction — that model's `recipientId = trip owner` invariant is load-bearing across many existing routes (ownership checks on accept/decline/confirm-seat/release-seat, the `/connections` Sent/Received tabs); inverting it for an owner-initiated case would corrupt that rather than simplify anything. No DB-level uniqueness on `(tripId, recipientId)`, same "only a pending duplicate blocks a fresh attempt" tradeoff as `ConnectionRequest`.
- **`POST /api/seat-offers`** (body `{ conversationId }`): caller must be that conversation's trip owner (403 otherwise); `recipientId` is derived from the conversation's own participants (the other one), never trusted from the body. Rejects a non-upcoming trip, zero seats remaining, a block between the two parties (same check `POST /api/conversations`/`POST /api/connection-requests` already use), and a duplicate pending offer to the same recipient (409).
- **`POST /api/seat-offers/[id]/accept`**: caller must be `recipientId`. Unlike `ConnectionRequest` (accept, then a *separate* owner "Add as Participant" step via `confirm-seat`), accepting a `SeatOffer` **is** the seat confirmation — the offer already represents the owner's specific one-seat commitment, so accept atomically decrements `Trip.seatsRemaining` in the same transaction as the status flip, same guarded-`updateMany`-as-concurrency-guard idiom as `confirm-seat`.
- **`POST /api/seat-offers/[id]/decline`**: caller must be `recipientId`. No capacity change. **`POST /api/seat-offers/[id]/cancel`**: caller must be the trip owner rescinding their own still-pending offer (the inverse ownership check from accept/decline) — no notification, matching `ConnectionRequest` cancel's own precedent. **`POST /api/seat-offers/[id]/release-seat`**: caller must be the trip owner; mirrors `ConnectionRequest`'s own release-seat exactly (clears `seatConfirmedAt`, increments `seatsRemaining` back, `status` stays `accepted` as history, no upcoming-only restriction, no notification).
- **Three new `NotificationType` values** (`seat_offer_received`, `seat_offer_accepted`, `seat_offer_declined`) plus a fourth for trip cancellation (`seat_offer_trip_cancelled`, kept distinct from `trip_cancelled`/`request_trip_cancelled` for the identical `notificationLink()`-disambiguation reason those two are already distinct from each other — see the Request/Trip Matching Lifecycle section).
- **UI is an inline bubble inside the message thread itself, not a separate control above it** (per product decision, refined after the first pass): `SeatOfferBubble` (`src/components/SeatOfferBubble.tsx`) renders one `SeatOffer` as a chat-bubble-styled `<li>` inside `MessageThread`'s own `<ul className="message-thread">`, positioned chronologically among real `Message`s by `createdAt` (a unified, sorted `items` array built in `MessageThread`, not two separate lists) — its Accept/Decline (recipient, while pending)/Cancel (owner, while pending)/Remove (owner, once accepted) controls are clickable elements inside the bubble itself, and every bubble carries a timestamp via the same `.message-meta` styling real messages use, so the thread reads as one consistent, fully-timestamped stream. The owner's "Send Seat Request" trigger lives just above the compose box, only shown when there's no currently pending/accepted offer already (the active offer's own bubble already carries the relevant action). `GET /api/conversations/[id]/messages` (the existing 4s poll endpoint) now also returns the conversation's full current `seatOffers` list on every tick — not `since`-filtered like messages, since an accept/decline/cancel is an UPDATE that doesn't change `createdAt` — so an offer's status updates live for both parties without a page reload, the same as new messages already do. `MessageThread` owns `seatOffers` as local state (`useState(initialSeatOffers)`, updated via a `patch`-based `onUpdate` callback the bubble calls after each successful action, or wholesale-replaced by the poller), the same pattern `messages` state already used — this replaced the original design's separate `SeatOfferButton`/`RespondToSeatOfferButtons` components entirely (deleted), which lived above the thread and didn't sync live. On `/trips/[id]`, accepted `SeatOffer`s are still merged into the same "Participants" roster accepted `ConnectionRequest`s already populate (see Trip Participants above, unchanged) — `ConfirmSeatButton` remains generalized via a `{ id, kind }` pair so one component serves both.
- **`PATCH`/`DELETE /api/trips/[id]` both updated again** (a third mechanism now draws from the same `seatsRemaining` pool, after `ConnectionRequest` and the standalone-Request matching lifecycle): `PATCH`'s consumed-seats total now also counts accepted `SeatOffer`s (always 1 seat each); `DELETE` (cancel trip) now also flips pending `SeatOffer`s to `cancelled` and notifies both pending- and accepted-recipients (accepted ones keep their historical record untouched, same "don't delete historical data" precedent as the other two mechanisms).

## Request/Trip Matching Lifecycle

Fills in the other half of "getting a ride": a standalone `Request` (`tripId = null`, "requester posts first") can now actually get matched to a `Trip`. `requests/[id]/{accept,decline,complete}` are implemented, filling in the plan doc's stated lifecycle: `pending` → traveler `accepts` (capacity decremented transactionally if attached to a trip) or `declines` → accepted requests reach `completed`. This is a separate mechanism from `ConnectionRequest`/Trip Participants above, but **draws from the exact same `Trip.seatsRemaining` pool** — both must be accounted for together anywhere that pool is read or written.

- **`POST /api/requests/[id]/accept`**: body `{ tripId }`. Caller must be that Trip's own `travelerId` (403 otherwise) — proven by looking up the given `tripId`, since a standalone Request has no traveler to check ownership against until one accepts it. Rejects fulfilling your own request (400, same "can't act on your own X" convention as elsewhere), a non-`pending` request (400), and a non-upcoming trip (400, same `tripDisplayStatus` gate used everywhere else). Capacity check differs by `Request.type`: a `ride` request consumes `seatsRequested ?? 1` seats (**not** always 1 — unlike `ConnectionRequest.confirm-seat`, a standalone ride request can ask for more than one seat) via the same guarded-`updateMany`-as-concurrency-guard idiom as `confirm-seat` (`seatsRemaining: { gte: seatsNeeded }` → decrement, 0 rows affected → the whole `$transaction` throws); a `package` request only requires `Trip.packageSpaceAvailable === true` — there's no numeric package capacity to decrement. The same transaction also does a guarded `Request.updateMany({ where: { status: "pending" } })` first (0 rows → someone else already resolved it), so both writes share one all-or-nothing guard. On success, notifies `postedById` with a new `request_accepted` `NotificationType`.
- **`POST /api/requests/[id]/decline`**: same caller-identification (`{ tripId }`, ownership check) as accept, minus the capacity logic — just flips `status → declined`. **Deliberately has no UI button** for a standalone Request: `Request` is a single row, not per-viewer like `ConnectionRequest`, so any one traveler declining would end the request's life for every *other* traveler who might still want to fulfill it — exposing this to random viewers would be an easy griefing vector. Built for spec-completeness and a future "Request created directly against one specific Trip" case (not yet built), where declining really would only concern that one trip's owner.
- **`POST /api/requests/[id]/complete`**: callable by either participant (`postedById`, or — once `tripId` is attached — that Trip's `travelerId`), 403 otherwise. Requires `status === "accepted"` (400 otherwise). No capacity change (the seat/package space stays consumed permanently, same as Trip's own Mark Completed not returning anything) and **no notification** — matches the `MarkTripCompleteButton` precedent that a participant's own completion action isn't itself an event worth notifying the other side about. Deliberately not date-gated, same trust-the-marking-party precedent as Trip's own Mark Completed. This is what unlocks Review eligibility (`Review` requires `Request.status = completed`) — see the Reviews section below.
- **Two new `NotificationType` values, not a reuse of `trip_cancelled`**: `request_accepted` (sent on accept, above) and `request_trip_cancelled` (sent when `DELETE /api/trips/[id]` cancels a trip that has an `accepted` standalone Request attached — see below). `notificationLink()` (`src/lib/notifications.ts`) is a synchronous `{type, relatedId} → url` mapper with no DB access, and its existing `trip_cancelled` case is hardcoded to `/connections?tab=sent` because `relatedId` there is always a `ConnectionRequest.id`; reusing that same type for a `Request.id` would send the notification to the wrong page with no way to disambiguate the two id spaces. Both new cases instead resolve to `/requests/${relatedId}`. (Migration `20260827003830_add_request_matching_notification_types` — two additive `ALTER TYPE ... ADD VALUE` statements, same mechanic as `trip_cancelled`/`trip_seat_confirmed` before it. `src/components/NotificationItem.tsx`'s `NOTIFICATION_ICONS` map is `Record<NotificationType, string>`, so it required an entry for each new value too, or the build breaks.)
- **`PATCH`/`DELETE /api/trips/[id]` both had to account for Request-consumed seats alongside `ConnectionRequest.seatConfirmedAt`**, since both draw from the same `seatsRemaining` pool: `PATCH`'s `confirmedParticipantCount` now also sums `seatsRequested ?? 1` across `accepted`/`completed` ride-type Requests on that trip (a plain JS reduce, not a SQL `_sum`, since a SQL sum would skip `NULL`s) before deciding whether the new `seatsTotal` is even allowed. `DELETE` (cancel trip) now also notifies (`request_trip_cancelled`) any `Request.postedById` whose `accepted` Request is attached to the cancelled trip — their Request's `status` is left untouched (`"accepted"`), same "don't delete historical data" precedent as the `ConnectionRequest` handling right above it in that route.
- **UI**: `/requests/[id]` shows a `FulfillRequestForm` (`src/components/FulfillRequestForm.tsx`) to a non-owner viewer of a still-`pending`, `tripId = null` Request, letting them pick one of their own eligible upcoming Trips (package requests are pre-filtered to `packageSpaceAvailable: true` — a hard capacity precondition, not a "matching/search" heuristic, which stays out of scope everywhere else in this app) and accept. Once accepted/completed, the same page shows who's fulfilling it plus `MarkRequestCompleteButton` (`src/components/MarkRequestCompleteButton.tsx`, a near-clone of `MarkTripCompleteButton`) to whichever of the two participants is viewing. `/trips/[id]` gets a parallel owner-only "Requests You're Fulfilling" section (same shape as Participants, reusing `PosterBadge`) listing every `Request` matched to that trip. `/my-posts` gets an inline `MarkRequestCompleteButton` next to an `accepted` Request. All three surfaces POST to the same `/api/requests/[id]/complete`.
- **Deliberately out of scope for this pass**: blocking (`isBlockedBetween`, see Block a User above) is not checked anywhere in this lifecycle — consistent with `ConnectionRequest`'s own accept/decline/cancel not checking blocks either (only creation does).

## Reviews

`POST /api/reviews` is implemented, filling in the last real stub in the core trip/request lifecycle. A completed `Request` has exactly two participants — whoever posted it (`postedById`; `beneficiaryId` is identical to it today, since on-behalf-of-student posting isn't wired up) and the Trip that fulfilled it (`Trip.travelerId`, via `Request.tripId`) — and each can independently review the other, up to two `Review` rows per Request (one per direction), enforced by the schema's existing `@@unique([requestId, reviewerId])`. Because a Request can only reach `accepted`/`completed` through `POST /api/requests/[id]/accept` (which always sets `tripId` in the same write as the status change — see Request/Trip Matching Lifecycle above), a `completed` Request is guaranteed to have `tripId` set, so the route needs no defensive null-handling around that.

- **Scope, deliberately narrow**: this pass is request-thread only — submit a review and see both directions' reviews on `/requests/[id]`. It does **not** touch `/profile`, `/profile/[userId]`, or `getPublicProfile()` — profile-level rating aggregation (the plan doc's "aggregate rating, completed trip/delivery counts" public-profile fields) was already explicitly deferred as a separate future feature (see the comment on `/profile`'s own page), and this pass respects that boundary rather than expanding it. The plan doc itself says MVP can compute any aggregate on read rather than storing one — that's still true and unaffected by this pass, since no aggregate is computed anywhere yet.
- **`POST /api/reviews`**: body `{ requestId, rating (1-5 int), comment? }`. Rejection order: `getCurrentUser()` → 401; bad body → 400; `Request` not found → 404; `status !== "completed"` → 400; neither `postedById` nor (`tripId` set and) the Trip's `travelerId` → **403** (not a participant, same "wrong caller against someone else's resource" convention 403 is reserved for elsewhere in this app); `revieweeId` is derived server-side from the caller's role (never trusted from the body, same non-spoofable pattern as `POST /api/connection-requests`) — a same-person guard (`revieweeId === user.id` → 400) exists defensively even though it's unreachable in practice, since `accept` already blocks fulfilling your own request. An **explicit** pre-check for an existing `(requestId, reviewerId)` row (via the Prisma-generated `requestId_reviewerId` compound-unique lookup) returns **409** before attempting create, same "check it explicitly for a clean error" convention the stub's own original TODO called for, rather than relying on the raw `@@unique` violation. On success, notifies `revieweeId` with a new `review_received` `NotificationType`.
- **`review_received`**: a new `NotificationType` value (migration `20260827033557_add_review_received_notification_type`), kept distinct from `request_accepted`/`request_trip_cancelled` even though it resolves to the exact same destination in `notificationLink()` (`/requests/${relatedId}`) — it's a semantically different event, and `notificationLink()` dispatches purely on `type`, so reusing an existing value here would just be reuse for reuse's sake, not a functional necessity the way avoiding a `trip_cancelled` reuse was for the Request/Trip Matching Lifecycle above. `src/components/NotificationItem.tsx`'s `NOTIFICATION_ICONS` map needed a `review_received: "⭐"` entry too, same hard-build-requirement pattern as every prior `NotificationType` addition.
- **UI**: `/requests/[id]`'s existing `found.status === "completed"` branch (previously rendering only the "Being fulfilled by..." sentence) gained a new block, gated to the two actual participants (`isOwner || isTripOwner`, reusing the page's existing role variables — no separate `isBeneficiary` check, since it's identical to `isOwner` today): shows the counterpart's review of you if they've left one, and either your own already-submitted review or a `ReviewForm` (`src/components/ReviewForm.tsx`) if not. Both directions render unconditionally and independently — no blinding one review until the other exists, keeping this the same "no invented mechanics beyond what the schema already models" as everywhere else in this app. `ReviewForm` is always-visible (not reveal-on-click like `ReportButton`/`ConnectionRequestButton`) since it only ever renders in this one already-narrowly-gated state, so there's no clutter to hide behind an extra click; its rating `<select>` has a disabled default option (same "can't submit without an explicit choice" pattern as `ReportButton`'s reason dropdown) to avoid silently defaulting to a specific star rating.

## Report a User

A user can report another user, optionally in the context of a trip, request, or message thread, for **manual** admin review — there is no admin/moderator concept or moderation queue UI anywhere in this app yet, so `POST /api/reports` has zero automated consequence of any kind: no suspension, no notification, no email, no report-count surfaced anywhere (not on a profile, not anywhere else). A `Report` row is `status = open` on creation and stays that way until someone edits it directly via Prisma Studio/DB access — nothing in this feature ever transitions it. Per the plan doc's Flow F ("Report enters an admin moderation queue — manual review for MVP"), this is intentionally write-only.

- **`ReportButton`** (`src/components/ReportButton.tsx`) is the one shared control, mounted from four places, each passing a different `contextType`/`contextId` pair: `/profile/[userId]` (`"profile"`, no `contextId` — there's no separate entity beyond the user itself), `/trips/[id]` (`"trip"`, the trip's id), `/requests/[id]` (`"request"`, the request's id), and `/messages/[id]` (`"message"`, the **conversation's** id, not a single message — the product framing is "report this person, in the context of this thread," not "report this one message"). Each mount is gated so a user never sees a control to report themselves (`viewer.id !== userId` on the profile page, `!isOwner` on trip/request, `counterpart &&` on messages — every conversation is 2-party, so `counterpart` is always the other person). Trip/Request mounts are deliberately **not** further gated by upcoming/active status, unlike `ConnectionRequestButton` — reporting someone's behavior should stay possible even once their post is cancelled or completed.
- Same reveal-on-click composer shape as `ConnectionRequestButton` (reusing its `.connection-request-compose` CSS class as-is), but **no `confirm()` dialog**: submitting isn't destructive to the reporter and has zero automated consequence for the reported user, unlike `DeletePostButton`'s confirm()-gated actions (all irreversible changes to the caller's *own* resource). The friction gate instead is a **required** reason `<select>` with no default, same "can't submit with one click" bar `ConnectionRequestButton`'s own required note now uses.
- **`POST /api/reports`**: `reporterId` always derived from `getCurrentUser()`, never trusted from the body, same non-spoofable pattern as `POST /api/connection-requests`. `reason` is a small fixed vocabulary (`spam` / `harassment` / `unsafe_behavior` / `scam_or_fraud` / `inappropriate_content` / `other`) even though `Report.reason` is a plain `String` column with no DB enum — free-form nuance belongs in the optional `detail` field instead; a fixed set is what keeps a future moderation queue scannable without a migration. Rejects a self-report (`reportedUserId === caller.id`) with **400**, not 403 — this codebase reserves 403 for "wrong caller against someone else's resource" and uses 400 for "can't target your own X" (matching `POST /api/connection-requests`'s "can't request to connect on your own trip"). 404s if `reportedUserId` doesn't resolve to a real `User` (avoids a raw FK-violation 500 at insert time). `contextId` is deliberately **never** validated against the underlying `Trip`/`Request`/`Message` — those rows can legitimately be cancelled/deleted later and a report should still stand as history, and cross-checking three different entity types for what's currently just free-text context for a moderator who doesn't exist yet isn't worth it. No DB-level uniqueness on `(reporterId, reportedUserId)` — the same reporter can file more than one report against the same user (different incidents), same "not worth a partial unique index" calibration as `ConnectionRequest`.
- **Explicitly out of scope**: no admin/moderation UI or route of any kind, no automated suspension or other consequence taken on a report regardless of volume or reason, no report-specific rate limiting (`src/lib/rate-limit.ts` stays scoped to Trip/Request posting only — a known, deliberately deferred gap, not an oversight).

## Block a User

Implements the plan doc's Flow F "Block" half (§7, Decisions Log #13) — a one-directional `Block` row (`blockerId` → `blockedId`, already in `prisma/schema.prisma` pre-migration, no schema change needed to build this) that is **enforced bidirectionally** everywhere it matters: a blocked user disappears from the blocker's Explore results *and vice versa*, and neither party can start a new conversation or connection request with the other, regardless of who initiated the block. Unlike Report, blocking has a real, immediately visible effect and is fully reversible (unblock).

- **`src/lib/blocks.ts`** is the single place the bidirectional check lives: `isBlockedBetween(userIdA, userIdB)` (used by every route/page gate below) and `getBlockedCounterpartIds(userId)` (used once by Explore to filter both the Trip and Request queries in one pass, rather than per-card).
- **`BlockButton`** (`src/components/BlockButton.tsx`) is mounted in the exact same four places as `ReportButton` (`/profile/[userId]`, `/trips/[id]`, `/requests/[id]`, `/messages/[id]`), each server component computing `initialBlocked` via `isBlockedBetween` so the button renders as "Block user" or "Unblock user" without a client-side fetch. Unlike `ReportButton`, this **is** `confirm()`-gated — blocking has a visible effect on both parties — but the copy frames it as reversible ("You can unblock them later"), not as a `DeletePostButton`-style irreversible warning.
- **`POST /api/blocks`** (body `{ blockedId }`): `blockerId` always derived from `getCurrentUser()`, never the body, same non-spoofable pattern as `POST /api/reports`. Self-block is 400 (not 403, matching the existing "can't target your own X" convention), a nonexistent `blockedId` is 404. A duplicate block is a plain `upsert` no-op, not a 409 — there's no "try blocking again" flow worth protecting the way `ConnectionRequest`'s pending-duplicate check is.
- **`DELETE /api/blocks/[blockedId]`** (unblock): scoped `deleteMany({ blockerId: caller, blockedId })` where 0 rows affected → 404, the same `updateMany`/`deleteMany`-as-authorization idiom already used by `POST /api/conversations/[id]/read` and `POST /api/notifications/[id]/read`. No `GET /api/blocks` route exists — the one place blocked users are listed (`/profile`'s "Blocked Users" section) is a server component and queries Prisma directly, the same convention `/my-posts`/`/connections` already use.
- **Enforcement points**: `POST /api/conversations` and `POST /api/connection-requests` both reject (403) if `isBlockedBetween(caller, trip.travelerId)`; `POST /api/connection-requests/[id]/accept` re-checks the same thing between `requesterId`/`recipientId` as defense-in-depth, since a block can happen after a request goes pending but before it's accepted — accepting would otherwise create exactly the new `Conversation` a block is supposed to prevent. `/explore` filters both its Trip and Request queries with `notIn: blockedUserIds` alongside the existing `not: user.id` self-exclusion.
- **Deliberately not touched**: an existing `Conversation`/`Message` history or completed-trip/review history that predates a block stays fully visible and usable — only *new* conversations/connection requests are blocked, matching the plan doc's explicit "Existing completed trip history and reviews... remain visible" resolution (Decisions Log #13). Trip/Request *detail pages* (as opposed to Explore) aren't hidden from a blocked counterpart either — the plan doc only calls out "search/Explore," not direct-link access.

**Payment safety notice**: `/messages/[id]` (`src/app/messages/[id]/page.tsx`) renders a static `.chat-safety-notice` banner above every conversation thread, every time it's opened — reminding both parties that any money (gas contribution, delivery fee, etc.) is handled in person at the time of the ride/pickup, since this app has no payment/escrow infrastructure at all (see "No payment fields" below). It's plain server-rendered markup with no dismiss/acknowledge state — the goal is that the warning is always the first thing visible above the chat, not a one-time interstitial to click past.

## Architecture Summary

**Core entities** (`prisma/schema.prisma`): `User`, `VerificationRecord`, `SupportedUniversityDomain`, `StudentRecord`, `ParentStudentOtpRequest`, `ParentStudentInvite`, `ParentStudentLink`, `Region`, `City`, `RouteCommunity`, `Trip`, `Request`, `Conversation`/`ConversationParticipant`/`Message`, `ConnectionRequest`, `Notification`, `Review`, `Report`, `Block`.

**Design principles baked into the schema — do not casually "simplify" these away:**
- **Verification is composable, not singular.** `VerificationRecord.type` (`email` | `university` | `parent_relationship` | `identity`) lets badges exist independently. University verification is a hard product-level gate on student accounts, enforced in application logic — not a schema constraint — so a future `identity` (government ID) verification type slots in without migration.
- **Role lives on the action.** `Trip.travelerId` and `Request.postedById`/`beneficiaryId` don't care whether the user is a student, parent, or alumni.
- **A `User` account and a `StudentRecord` are separate concepts.** A `StudentRecord` can exist with no `User` at all (a parent created it first) — see the Parent/Student Linking section below. Parents now fully self-signup (no invite required), but `ParentStudentLink` is a verification fact, never an access grant: a parent's own capabilities are never blocked by link status, only the narrow "post a Request for this student" capability is, and even that isn't blocked pending some distant future approval — see the security tradeoff writeup below before changing this.
- **Routes are open, not gated.** `RouteCommunity.active` controls what Home *features* by default (Bay Area ↔ UCI), not what can be posted — `Trip`/`Request` can use any `City`, including ones outside the seeded regions (e.g. an airport for a UCI→LAX post).
- **`Request.trip_id` is nullable.** Supports "requester posts first" (a standalone need, not yet matched to a trip) alongside "traveler posts first."
- **Reviews are fraud-resistant by construction.** A `Review` requires `Request.status = completed`, both parties must be participants of that request, and `(requestId, reviewerId)` is unique — enforce these as DB constraints, not just app checks.
- **No payment fields.** `Trip.tripNotes` is free text describing the trip itself (e.g. "driving my own car"), never a contribution/gas-money mechanism — MVP explicitly excludes payment infrastructure.
- **Anti-spam:** cap of 10 new `Trip`/`Request` creations per user per rolling 12-hour window (`src/lib/rate-limit.ts`).

Note `connection-requests/[id]/accept` is a different, already-implemented thing from `requests/[id]/accept` — the former accepts a `ConnectionRequest` (a Trip-first flow), the latter accepts a standalone `Request` against a `Trip` (a Request-first flow) — don't conflate them.

**Windows dev-server gotcha, confirmed this session:** if `npm run dev` is ever force-killed (`Stop-Process -Force`, Task Manager, a crashed terminal) rather than allowed to exit normally, the webpack persistent cache under `.next/cache` can end up torn. The symptom is oddly specific and easy to misread as an application bug: one particular route consistently 500s with `Jest worker encountered N child process exceptions, exceeding retry limit` in the server log, while the exact same Prisma query run standalone (outside Next.js) succeeds instantly — i.e. the data layer is provably fine and it's still failing. Fix: stop the dev server and `rm -rf .next` before restarting. Avoid force-killing `next dev` when there's a graceful alternative (closing the terminal / normal Ctrl-C) to reduce how often this recurs.

## Environment Variables

Copy `.env.example` to `.env` (never fill real values into `.env.example` itself — it's committed to the repo) and fill in:
- `DATABASE_URL` / `DIRECT_URL` — Postgres connection strings (Supabase provides both). See the comments in `.env.example` for two non-obvious gotchas already hit once: `DATABASE_URL` needs `?pgbouncer=true` (transaction-pooler prepared-statement conflicts), and `DIRECT_URL` should point at the session pooler (port 5432, same host as `DATABASE_URL`) rather than Supabase's plain `db.<ref>.supabase.co` host, which is IPv6-only and unreachable from IPv4-only networks.
- `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` — Supabase client config
- `SUPABASE_SERVICE_ROLE_KEY` — server-only, never expose to the client. Used by `src/lib/supabase/admin.ts`, which now backs several things beyond its original one purpose: parent signup's pre-confirmed account creation, avatar uploads (`src/lib/supabase/storage.ts`), and setting/clearing the `hasLinkedStudent` `app_metadata` flag the parent-link gate's middleware check reads (see Auth Architecture).
- `RESEND_API_KEY` / `EMAIL_FROM` — transactional email for verification + invite links. Optional: without it, `src/lib/email.ts` logs the verification link to the console instead of sending it, which is fine for local dev.
