## Project Overview

CampusConnect is a trusted community marketplace connecting students, parents, alumni, and travelers moving between a student's home area and college — launching with **Bay Area ↔ UC Irvine**. Users are not permanently a "driver": the same account can offer a personal-car ride one week and split an Uber the next. Role lives on the action (`Trip`), not on the `User`. There is no standalone "need a ride" posting flow — only offering a ride/split/package space is supported (see Trip Categories & Package Carrying below for why the "Need" flow was removed).

## Auth Architecture

Supabase Auth owns account credentials (`auth.users`); Prisma's `User` table is a separate, app-owned table keyed on the **same id** (`User.id = auth.users.id`). Nothing in Prisma generates that id — it's always the Supabase-issued UUID, written by app code.

- **Signup** (`src/app/(auth)/sign-up/page.tsx`, client component) starts with a persona picker (Student / Parent / Alumni / Traveler) that is **NOT a stored/permanent role** (USER != ROLE) — it only decides the post-confirmation redirect. Student/Alumni/Traveler all go through the identical `supabase.auth.signUp()` flow described below and land on `/onboarding` (a soft-nudge profile-completion step, see Profile & Onboarding below — not Home directly); Parent goes through the same signup mechanics but lands on `/family/connect-student` next (see the Parent/Student Linking section below). The signup email itself doubles as the university-verification input for a Student. Confirmation offers **two independent paths**, both leading to the same place:
  - **Link**: the email's `emailRedirectTo: {origin}/auth/callback` link. `src/app/auth/callback/route.ts` exchanges the PKCE `code` for a session, then calls `syncUserFromAuth`.
  - **OTP code**: the sign-up page also shows a numeric code input right after submitting (Supabase's default email OTP is 8 digits — the input's `maxLength` learned this the hard way, don't hardcode a shorter length). The client calls `supabase.auth.verifyOtp({ email, token, type: 'signup' })` directly (no server route involved in the verification itself), then `POST /api/auth/sync` to run the same `syncUserFromAuth` bridge against the now-cookie-authenticated session.
  - **Why both exist:** some university (and corporate) mail gateways pre-fetch every link in incoming email to scan it, which silently consumes the link's single-use token before the real user clicks it — confirmed in this project via a real test where Supabase's own `confirmation_sent_at`/`email_confirmed_at` were 7 seconds apart, not humanly possible. The link still works fine for domains without that behavior; the code is the reliable fallback, since a scanner can't type a code into a form. **For the code to actually appear in the email, the "Confirm signup" template must be edited in the Supabase dashboard (Authentication → Emails → Templates) to include `{{ .Token }}`** — by default Supabase's template only shows the link.
- **`src/lib/onboarding.ts`**'s `syncUserFromAuth(authUser)` is the single place that bridges a confirmed Supabase Auth user into Prisma — both the link and OTP paths call it, so the Prisma-write logic exists exactly once. It upserts the `User` row and `VerificationRecord(type=email, status=verified)` (reaching either path already proves Supabase confirmed the email), then checks the confirmed email's domain against `SupportedUniversityDomain` and upserts `VerificationRecord(type=university, status=verified)` in the same call if it matches — someone who signs up with `you@uci.edu` lands on Home already fully verified, no second step. **Same call also claims-or-creates their `StudentRecord`** via `claimOrCreateStudentRecord` (see the Parent/Student Linking section) — this is what lets a student who signs up later automatically attach to a record a parent already created. This merged design was a deliberate simplification made mid-build (see git history) after the original plan doc's two-step design (separate `.edu` entry post-signup) proved more failure-prone in practice than it was worth.
- **`/verify`** (`src/app/verify/page.tsx`) still exists as a **self-serve fallback**, not the primary path: for anyone who signed up with a personal email and wants to add a university badge later (e.g. an alum, or a student who typo'd their domain at signup). It posts to `/api/verification/university/request` (checks the domain against `SupportedUniversityDomain`, emails a single-use expiring token) and, when landed on with `?token=`, to `/api/verification/university/confirm`. This is one of two paths where `src/lib/email.ts` actually sends an email (the other is the parent-connection OTP/notice emails below) — the merged signup flow never calls it, since Supabase's own confirmation email already covers that trip.
- **`src/middleware.ts`** + **`src/lib/supabase/middleware.ts`** refresh the session cookie on every request — required by the `@supabase/ssr` pattern since Server Components can't write cookies themselves.
- **`src/lib/supabase/client.ts`** / **`server.ts`** are the two Supabase client constructors (browser vs. cookie-reading server); **`src/lib/auth.ts`**'s `getCurrentUser()` is the one place that joins a Supabase session to a Prisma `User` (with `verifications`, `parentLinksAsParent` (incl. nested `studentRecord`), `homeCity`, and `studentRecord` all included) — use it from Server Components/route handlers rather than calling Supabase directly, so verification-badge logic stays in one place (see `isUniversityVerified` / `universityBadgeLabel` / `parentRelationshipBadgeLabel`).
- Login (`/login`) and sign-out (`POST /api/auth/signout`) are minimal, included because an auth setup isn't testable without them — kept intentionally small.

**Two entry gates exist, enforced differently:**
- **Parent-signup accounts (`User.signedUpAsParent = true`)**: cannot reach *any* other page until `hasLinkedStudent(user)` is true (linked to at least one student, any student, via OTP or an accepted invite). `/family/connect-student` and `/family/invite/accept` are the only exempt paths (see the Family Page section below for why the second one exists). This is a real, currently-working gate — **but it is enforced in two places, not one, and both are load-bearing**:
  - `src/app/layout.tsx` does the DB-backed check (`hasLinkedStudent(user)` against Prisma) and `redirect()`s — this is what runs on the very first full page load.
  - `src/lib/supabase/middleware.ts` (`updateSession`, called from `src/middleware.ts` on every request) does a *second*, independent check on every navigation, including client-side `<Link>` transitions. This turned out to be necessary, not redundant: Next.js App Router layouts are **not re-executed on client-side navigation** that keeps the same layout, so a gate living only in `layout.tsx` only actually fires on the first load — a gated parent could click straight into Home/Post afterward once past that first render. Middleware can't query Prisma directly here (this project's installed Next.js version does not actually register middleware when `export const config = { runtime: "nodejs" }` is set, despite that being the documented syntax for stable Node.js middleware — confirmed by reproducing an empty `middleware-manifest.json` in `next build` output), so it instead checks a denormalized `hasLinkedStudent: boolean` cached on the Supabase Auth user's `app_metadata`. `src/app/api/family/parent-link/confirm/route.ts` sets that flag to `true` the moment a link is created; `src/app/api/family/link-objection/[token]/reject/route.ts` clears it back to `false` if a revocation leaves the parent with zero non-revoked links. Prisma's `ParentStudentLink` rows remain the actual source of truth (`hasLinkedStudent()` in `src/lib/auth.ts`, used by the `layout.tsx` check and everywhere else) — the `app_metadata` flag is only a fast, edge-readable copy for this one gate.
- **Posting (Trip/PackagePost creation) is implemented; university-verification and on-behalf-of-student posting are still deliberately deferred.** `/api/trips` and `/api/package-posts` have working `POST`/`GET`/`PATCH`/DELETE-as-cancel handlers (see the Trip Posting System section below) — but neither checks `isUniversityVerified(user)` yet (a product decision to defer this, made explicitly so testing isn't blocked by unverified test accounts, not an oversight), and every Trip post is self-authored (`travelerId` is always the poster) — there is no beneficiary/on-behalf-of-student concept anywhere in this schema. Messaging (`conversations`) is implemented (see the Messaging section below). `isUniversityVerified(user)` still isn't wired in: check it server-side before any student write, whenever that deferred work happens. Don't confuse this finer-grained per-student check with the coarser `hasLinkedStudent` app-wide gate above — they answer different questions ("can this parent act for *this* student" vs. "can this parent use the app *at all*").

## Parent/Student Linking (StudentRecord Architecture)

**Core problem this solves:** a parent may want to use CampusConnect before their student ever creates an account — the old model (`ParentStudentLink` pointing straight at a `User`) made that impossible. `StudentRecord` (`prisma/schema.prisma`) is a student identified by university email that can exist with **no** `User` account at all (`userId` nullable). `ParentStudentLink` now points at `StudentRecord`, not `User` — this is what lets an existing link stay valid automatically once the student eventually signs up, no relinking needed.

- **Duplicate prevention is entirely load-bearing on `StudentRecord.universityEmail` being `@unique`, plus the *pattern* used around it** — see the extensive comments on `claimOrCreateStudentRecord` (`src/lib/onboarding.ts`). Two distinct races matter and are both handled: (1) two concurrent *creates* for the same email (real `@unique`-backed create, with a caught-`P2002`-then-refetch fallback — **not** a naive find-then-create, which would race); (2) two concurrent *claims* of the same unclaimed record (a conditional `updateMany(WHERE userId IS NULL)`, since the `userId @unique` constraint alone only stops one `User` claiming two records, not two claims racing on one record). Both races were verified against the real database during development (concurrent `Promise.all` calls into `claimOrCreateStudentRecord`, confirming a single row results either way) — don't remove that rigor when touching this function; there's no automated DB-backed test for it yet (see the Automated Tests section — this project's test suite so far only covers pure, DB-free functions), so re-verify by hand if you change it.
- **Every path that can create or claim a `StudentRecord` MUST go through `claimOrCreateStudentRecord`** — never a bespoke find-then-create. Currently two callers: `syncUserFromAuth` (a student's own signup) and `src/app/api/family/parent-link/confirm/route.ts` (a parent's OTP confirm).
- **Parent signup skips email confirmation entirely** — `/api/auth/parent-signup` creates the Supabase Auth user via the admin API (`src/lib/supabase/admin.ts`, service-role key, server-only) with `email_confirm: true`, so a parent never clicks a link or enters a code for their own email; the client immediately calls `signInWithPassword` then `/api/auth/sync`. This is a narrow bypass scoped to that one route, not a project-wide Supabase setting change — the Student path's own confirm flow (link/code, described above) is completely unaffected and stays fully rigorous, since a student's email confirmation doubles as their university verification. A parent's own email isn't the security-critical fact in this product; the student's is.
- **Parent flow**: `/family/connect-student` (parent-facing, two steps on one page) → `POST /api/family/parent-link/request` (caller just needs to be authenticated — no email-verification precondition, per the above — validates the student email's domain against `SupportedUniversityDomain`, creates a `ParentStudentOtpRequest` — an *ephemeral* pending row, deliberately not touching `StudentRecord` yet so a typo'd email never leaves an orphan record — and emails an 8-digit code to the **student's** inbox, not the parent's) → `POST /api/family/parent-link/confirm` (validates the code against a hash with attempt-limiting, then calls `claimOrCreateStudentRecord` and creates `ParentStudentLink(status=otp_verified)`).
- **Why a custom OTP instead of Supabase's**: Supabase's OTP is inherently tied to the auth account being signed into/created for that email — it can't send a code to a third party's inbox on someone else's behalf. `src/lib/otp.ts` + the `request`/`confirm` routes reuse the exact pattern already built for `/api/verification/university/{request,confirm}`, just with a short numeric code (hashed at rest — unlike the long hex tokens elsewhere, an 8-digit code is meaningfully brute-forceable, hence `OTP_MAX_ATTEMPTS` + a ~20 min expiry) instead of a link.
- **No on-behalf-of-student posting exists at all**: there is no beneficiary concept anywhere in this schema — `Trip.travelerId` is always the poster's own id, parent or otherwise. This used to be a live security tradeoff back when a standalone `Request` model existed with a separate `beneficiaryId`, letting a parent post "for" the student the moment `otp_verified` was reached; that `Request` model (and the whole "Need" posting flow it powered) has since been removed entirely (see Trip Categories & Package Carrying below), which removed the tradeoff along with it. `ParentStudentLink` today is a pure verification/relationship *fact*, not an access grant of any kind — it doesn't let a parent post anything a non-linked user couldn't already post, doesn't make the student a `ConversationParticipant`, and doesn't merge the two accounts in any way. The student notice email with the no-account-required objection link (`/family/link-objection` + `POST /api/family/link-objection/[token]/reject`) still exists as a courtesy notification of the link itself, not as a revoke-a-live-capability safety valve.
- **Both directions of parent/student linking are now implemented**: `POST /api/family/link/[id]/approve` (the student's explicit upgrade from `otp_verified` to full trust, parent-initiated OTP flow) and the reverse student-initiated invite flow (`POST /api/family/invite` / `.../invite/accept`) — see the Parent Link Approval and Family Page sections below.

## Parent Link Approval

`POST /api/family/link/[id]/approve` is implemented — the student's explicit upgrade of an existing `ParentStudentLink` from `otp_verified` to `approved`, for links created via the **parent**-initiated OTP flow (the student-initiated invite direction below never needs this, since it's created at `approved` already). Caller must be `link.studentRecord.userId` (403 otherwise), and only an `otp_verified` link can be approved (400 for already-`approved` or `revoked`) — a guarded `updateMany` doubles as the concurrency check, same idiom used everywhere else in this codebase. **Deliberately does not wire a `VerificationRecord` on either user** — the original stub comment only hedged ("*consider*..."), and there's no student-side badge concept or UI slot anywhere to display one; the parent already got their `parent_relationship` badge back at `otp_verified` time (`parent-link/confirm/route.ts`), so nothing new is needed on that side either. Notifies the parent (`parent_link_approved` `NotificationType`, `relatedId` unused/null — no per-link page exists to deep-link to, so `notificationLink()` routes it to `/profile`, where the parent's own "Linked Students" section already shows current status for every link they have).

## Family Page (Management Hub)

`/family` (`src/app/family/page.tsx`) is the **student's** interactive management hub for both directions of parent/student linking — distinct from the read-only "Linked Students" list on `/profile`, which stays a parent-facing, action-free view and is untouched by this page. A parent visiting `/family` is pointed to `/profile` instead of duplicating that list; a user with no `StudentRecord` at all (alumni/traveler) sees a neutral explanatory message.

- **"Parents Connected to You"**: every `ParentStudentLink` pointing at the caller's own `StudentRecord`, with an `ApproveLinkButton` (`src/components/ApproveLinkButton.tsx`, confirm()-gated, same "can't be undone" framing as `MarkTripCompleteButton`) shown only on `otp_verified` rows, plus a plain-text hint ("they proved access to your email — confirm this is really your parent/guardian") so the student has context before approving. Status badges reuse the existing `.connection-status-label-*` palette from `ConnectionRequest` (pending=amber, accepted=green, declined/cancelled=grey) rather than inventing new colors.
- **The student-initiated direction**: a student invites a parent/guardian by email (`ParentStudentInvite`, `POST /api/family/invite`) — the reverse of the parent-initiated OTP flow above. Caller must be `isUniversityVerified` (not just "has a `StudentRecord`" — a `StudentRecord` can exist unclaimed or claimed-but-unverified, and this is the one direction where the STUDENT is vouching, so their own verification is the meaningful gate). `/family` itself only shows the "Invite a Parent/Guardian" (`InviteParentForm.tsx`) and "Sent Invites" sections once `isUniversityVerified(user)` is true — an unverified student sees a link to `/verify` instead, so the invite form never appears somewhere it would just 403 on submit. Sends straight to the parent's own inbox via `sendParentInviteEmail` (`src/lib/email.ts`) with a 32-byte hex token, `expiresAt` 7 days out — no code, no proving inbox access, since the student is the one vouching here, asymmetric from the OTP flow on purpose. Re-inviting the same address clears the old **pending** invite first (same "clean up stale unconsumed state" convention `ParentStudentOtpRequest` uses), never touching an already-accepted/revoked row (real history). "Sent Invites" derives an `expired` display status at read time for a still-`pending`-in-the-DB invite past `expiresAt`, same "derived, never persisted" convention as `tripDisplayStatus`/`requestDisplayStatus` in `postStatus.ts`. **Rate limited**: `canSendFamilyInvite(userId)` (`src/lib/rate-limit.ts`) caps a student at 5 invites per rolling 24-hour window (429 if exceeded), checked right after the `isUniversityVerified` gate — added after a security audit noted that, unlike most writes in this app, each invite is a real Resend email send to an address of the caller's choosing, so unbounded spam here has a real send-cost and arbitrary-third-party-abuse angle (the pre-existing "clear the old pending invite" cleanup only dedupes re-invites to the *same* address, it doesn't cap looping over different ones).
- **`/family/invite/accept?token=...`** (`src/app/family/invite/accept/page.tsx`) is where that email links. Unlike `/family/link-objection`, this route *requires* an account — accepting only happens once the caller is signed in with the **exact** invited email (proven via their own Supabase signup/login, the same standard the OTP path uses for student-email access) — so it's a Server Component that calls `getCurrentUser()` directly rather than the public/no-auth client-only shape `link-objection` uses. Not-logged-in and wrong-account states both render an explanatory message rather than silently failing. The actual accept POST (`AcceptFamilyInviteButton.tsx`) requires an explicit button click, **never** fires on page load — same email-scanner-prefetch reasoning as `link-objection`, and arguably more important here since accepting grants `approved` (stronger trust) directly, not `otp_verified`.
- **Exempt from the parent-link gate**: `/family/invite/accept` was added alongside `/family/connect-student` in both `PARENT_LINK_GATE_EXEMPT_PATHS` (`src/app/layout.tsx` and `src/lib/supabase/middleware.ts`, kept in sync — see Auth Architecture above for why both places matter) — without this, a parent who signed up specifically to accept an invite would get bounced to the OTP wizard before ever reaching the accept page, since accepting an invite is an equally valid way to satisfy "has linked a student."
- **`POST /api/family/invite/accept`** creates `ParentStudentLink` at `status=approved` directly (not `otp_verified`) — the inviting student's own action is already unambiguous consent, asymmetric from the parent-initiated flow by design (see the security note on `ParentStudentLink` in `prisma/schema.prisma`). Same revoked-link guard as `parent-link/confirm` (a prior revocation can't silently re-establish via this route either), same `parent_relationship` `VerificationRecord` grant, same `hasLinkedStudent` `app_metadata` write. Notifies the inviting student on acceptance (`family_invite_accepted` `NotificationType`, links to `/family`) — the one event in this whole family-linking feature that fires a notification, since every other step already has its own feedback loop (the parent's own page state, the student notice email, etc.).
- **Deliberately not built**: an authenticated, in-page "remove this parent" action for the student (beyond the existing email-only `link-objection` token flow). Not one of the original stubbed TODOs this page filled in, and would need its own new revoke route with the same `app_metadata`/badge/`linkedStudentName` cleanup `link-objection/[token]/reject` already does — a reasonable follow-up, not assumed here.

## Profile & Onboarding

Post-signup, both personas fill in a profile before (student) or as part of (parent) their first real use of the app.

- **Student** (`/onboarding`, reached by default right after signup verification — see `postConfirmPath` in `src/app/(auth)/sign-up/page.tsx`): name (prefilled from signup, editable), optional photo, home city (`User.homeCityId`, a `City` FK — supersedes the older unused `homeRegionId`), and optional enrichment fields (`major`, `year`, `travelPreferences` as free text, `lookingFor` as a `String[]` multi-select against `src/lib/lookingFor.ts`'s `LOOKING_FOR_OPTIONS`, which reuses the Post page's own four categories). University name and the verified badge are never entered here — always derived read-only from `VerificationRecord`/`StudentRecord`. This is a **soft nudge, not a hard gate**: `layout.tsx` shows a "Finish setting up your profile" banner (`hasCompletedOnboarding(user)` in `src/lib/auth.ts`, keyed on `User.onboardingCompletedAt`) but never blocks navigation on it — deliberately, to stay consistent with "routes are open, not gated" and avoid the redirect-chain complexity the parent gate already has.
- **Parent** (step 0 of `/family/connect-student`, ahead of the existing student-email/OTP steps — skipped automatically if `hasCompletedOnboarding(user)` is already true, e.g. when linking a second student later): name, optional photo, home city, phone (private — same visibility tier as email, never on the public profile), and `linkedStudentName` (free text, **self-declared by the parent**, not derived from the private `StudentRecord.fullName` — public, so another user can see who a parent is posting on behalf of). `linkedStudentName` is cleared server-side the moment the parent's last non-revoked `ParentStudentLink` is removed via the student's own objection link (`src/app/api/family/link-objection/[token]/reject/route.ts`) — it can never outlive its backing connection, since it names a third party (the student) who isn't the one publishing it.
- **Shared form**: `src/components/ProfileEditForm.tsx`, used by all three entry points above plus self-editing on `/profile`, gated by an `isParent` prop that decides which of the persona-specific fields render. All three submit to the single `PATCH /api/profile` (multipart/form-data — the same route also handles the optional photo upload). `onboardingCompletedAt` is set there, once, the first time it succeeds for a given user.
- **Verification badges shown alongside the profile**: `universityBadgeLabel(user)` (existing, student/alumni self-verified) and `parentRelationshipBadgeLabel(user)` (new — `VerificationRecord(type=parent_relationship)`, granted in `parent-link/confirm/route.ts` the moment a link OTP-confirms, revoked there in `reject/route.ts` under the same "last link removed" condition as `linkedStudentName`). A parent's own email is never expected to be university-verified, so `layout.tsx`'s "Verify your university email" nudge is suppressed entirely for `signedUpAsParent` accounts.
- **Public vs. private**: `src/lib/profile.ts`'s `getPublicProfile(userId)` is the single hand-picked `select` allowlist (deliberately never `include`) shared by both `GET /api/profile/[userId]` and the public `/profile/[userId]` page — public fields are name, photo, university, general home area, `major`/`year`/`travelPreferences`/`lookingFor`, `linkedStudentName`, and verification badges; private fields (email, phone, `StudentRecord` contents, `ParentStudentLink` rows, `signedUpAsParent`) never appear there. Viewing another user's public profile requires being logged in (no fully public/unauthenticated directory).
- **Photos**: Supabase Storage, bucket `avatars` (public-read, 5MB/JPEG-PNG-WebP limits — see `src/lib/supabase/storage.ts`). The bucket doesn't exist by default on a fresh Supabase project; create/configure it via `npm run supabase:setup-storage` (`scripts/setup-storage.ts`).
- **`User.collegeName`**: still unused/deprecated, as before — university affiliation is always derived from the verified `StudentRecord`/`VerificationRecord`, never this field.

## Trip Categories & Package Carrying (Offer-Only)

CampusConnect only supports **offering** something — a ride (your own car), a split Uber/Lyft seat, or package space on your route. There is no standalone "need a ride"/"need something delivered" posting flow: a `Request` model used to power a parallel "Need" side of `/post` (post a standalone ask, get matched to a Trip later), and `PackagePost` used to carry a `needing_delivery` counterpart to its `offering_space` kind — both were **removed entirely** per direct product decision (the "Need" side "is essentially not useful and over-complicates it"). Only 3 offer actions remain.

- **Trips and Uber-sharing share one `Trip` model with a `category` discriminator (`TripCategory`: `personal_car` | `uber_share`), not two separate models.** The reason is structural, not a shortcut: `ConnectionRequest`, `SeatOffer`, and `Conversation` are all hard-wired to a scalar `tripId` FK straight to `Trip` (no polymorphic relation — Prisma doesn't support one). A `category` column costs one enum field, and every downstream consumer of `tripId` (`ConnectionRequest`, `SeatOffer`, `Conversation`, `src/lib/tripParticipants.ts`) needs zero logic changes to support it.
  - **`Trip` fields only meaningful when `category = uber_share`**: `estimatedFarePerSeat Decimal? @db.Decimal(6,2)` — a stated, informational per-seat cost, never a real payment (no escrow/payment infrastructure exists or is implied; same "settle up in person" principle as the `.chat-safety-notice` banner in `/messages/[id]`) — and `meetingPoint String? @db.VarChar(200)` — the one pickup spot everyone in a shared Uber needs to converge on. `seatsTotal`/`seatsRemaining` are shared unchanged by both categories.
- **`PackagePost` is a standalone, deliberately minimal model** — no structured description/size fields, no formal accept/decline handshake, no seat/capacity counter, and it never creates a `ConnectionRequest`/`SeatOffer` row. Fields: `originCityId`/`destinationCityId`/`destinationText` (same City-or-write-in convention as `Trip`), `date`/`time`/`flexibleTime`, a single optional `notes String? @db.VarChar(300)`, `studentsOnly`, `status` (`open` → `completed`/`cancelled`, poster marks it done manually, mirroring `MarkTripCompleteButton`'s pattern). It has **no `kind` field** — every `PackagePost` is implicitly "I have space for a package on my route," since the `needing_delivery` counterpart was removed along with the rest of the "Need" flow.
  - **The only interaction entry point is messaging** — `PackageMessageForm.tsx` mirrors `RegisterInterestForm`'s reveal-a-textarea-on-click shape exactly, posting `{ packagePostId, body }` to `POST /api/conversations` instead of `{ tripId, body }`. There is no formal request/accept step for a package post at all.
  - **`Conversation.tripId` is nullable**, paired with a nullable `packagePostId` — exactly one of the two is required, enforced app-level (never a DB constraint) in `findOrCreateConversationForPost` (`src/lib/messaging.ts`), the same "exactly one of X/Y" convention already used for `destinationCityId`/`destinationText`. `ConnectionRequest`/`SeatOffer` stay completely unchanged.
  - **API**: `src/app/api/package-posts/route.ts` (GET list, POST create), `[id]/route.ts` (GET/PATCH/DELETE-as-cancel), `[id]/complete/route.ts` — mirrors the shape of `src/app/api/trips/**` minus anything seat-related. **Pages**: `/post/package` (create), `/package-posts/[id]` + `/edit` (detail/edit, no seat/connection UI — the only action is `PackageMessageForm`), and a "Package Posts" section on `/my-posts`.
  - `canCreatePost` (`src/lib/rate-limit.ts`) counts `PackagePost` toward the same combined 10-per-12h cap as `Trip` — one shared anti-spam budget across both categories.
- **`/post`'s entry-point list is 3 actions, a single list (no Offer/Need split anymore)**: "Offer Package Space" (primary weight), "Split an Uber/Lyft" (secondary), "Offer a Ride (my car)" (tertiary) — see `POST_ACTIONS` in `src/app/post/page.tsx`. "Offer a Ride" and "Split an Uber/Lyft" both route to `/post/trip`, pre-selecting `category` via `?category=`; "Offer Package Space" routes to `/post/package` with no query param needed (there's nothing left to pre-select).
- **`Review` was removed along with `Request`**: `Review.requestId` was a required FK with no Trip-based alternative, so once the standalone `Request`/matching-lifecycle model was deleted, the whole Review feature (model, `POST /api/reviews`, `ReviewForm.tsx`) had no way to be triggered and was removed too, rather than redesigned to key off something else. There is currently no review/rating feature anywhere in the app.
- **`/explore` and Home browse `Trip` offers only** — no standalone-Request merging (there is no standalone Request to merge) and no `PackagePost` browsing yet; a package post is only reachable via a direct link (`/my-posts`, a notification, or a shared URL) once you know its id. See the Explore Page and Home Page sections below.

## Trip Posting System

Built on the `Trip` model — offers only, discriminated by `category` (see Trip Categories & Package Carrying above). `/api/trips` (`POST`/`GET`, plus `/[id]` for `GET`/`PATCH`/DELETE-as-cancel) is implemented. `conversations` (messaging) is also implemented, see the Messaging section below.

- **Entry point**: `/post` links to `TripPostForm.tsx` (Trip, both categories) and `PackagePostForm.tsx` (PackagePost) — see Trip Categories & Package Carrying above for the current 3-action list. Both used for create (`POST`) and edit (`PATCH`), same convention as `ProfileEditForm` (full-state submission, not partial patches). Shared Zod schemas live in `src/lib/postSchemas.ts`, not inside the route files themselves — Next.js's route export validation rejects any named export from a `route.ts` that isn't a recognized HTTP method or route config key, so a schema can't be exported directly from a route handler and imported elsewhere.
- **Ownership**: enforced in application code, not Postgres RLS (RLS is enabled schema-wide but carries zero policies and exists only to lock down Supabase's REST API — see the Architecture Summary's design-principles list; Prisma's connection bypasses it entirely regardless), the same pattern as the rest of the app — `getCurrentUser()` first, then an explicit `travelerId` comparison against the caller on every `PATCH`/DELETE.
- **Delete is a soft cancel** (`status → cancelled`), not a row removal — consistent with how every other lifecycle in this schema already works via a status enum, and avoids FK issues once `Conversation` rows reference a `Trip`.
- **Pages**: `/post/trip` (create), `/my-posts` (lists the caller's own Trips and PackagePosts, split into Upcoming/History tabs via `?tab=history` — Trips bucket by `tripDisplayStatus`, see the Trip Management section below), `/trips/[id]` (detail, Edit/Cancel shown only to the owner), `/trips/[id]/edit`.
- **Past-due status is derived, never persisted**: `src/lib/postStatus.ts`'s `tripDisplayStatus` computes an "expired" display state at read time for a non-terminal `upcoming` post whose date has passed, without writing to the DB `status` column — same pattern as `getPrimaryRouteLabel()` in `geo.ts`.
- **`Trip.title`**: a required (at the Zod layer; nullable in the DB since it postdates this model's earliest rows) short subject line stating the purpose of the post, shown as the page heading on `/trips/[id]` and in the `/my-posts` list.
- **Write-in destination**: `Trip.destinationCityId` is nullable, paired with `destinationText String?` — a poster can pick a listed `City` or type a destination that isn't seeded (e.g. an airport), never both. `tripFieldsSchema` (`src/lib/postSchemas.ts`) enforces "exactly one of the two" via `.refine()`, not a DB constraint. `TripPostForm` implements this as a `<select>` with a sentinel `"Other (type it in)"` option that reveals a free-text input. Origin stays City-only — this only applies to the destination side.
- **Students-only visibility** (`Trip.studentsOnly`, migration `20260828180000_add_students_only_posts`): an optional per-post flag restricting a post to other students only. "A student" is deliberately the precise, existing schema concept — `hasStudentRecord(user)` (`src/lib/auth.ts`), true only for an account with a claimed `StudentRecord` (signed up with, or later verified, an actual university email) — not the broader "didn't sign up as a parent," so an alumni/traveler account with no verified university email doesn't qualify either. A per-post flag, not a `User`-level setting, consistent with "role lives on the action" elsewhere in this schema. Enforced at every layer, not just hidden in the UI:
  - **Creation/edit**: `POST`/`PATCH` on `/api/trips` rejects `studentsOnly: true` from a non-student caller (403) — `TripPostForm` takes an `isStudent` prop and only renders the "🎓 Visible to students only" checkbox at all when true, purely to avoid offering a control that would just 403 on submit.
  - **Discovery**: `/explore` and `/` (Home) both add `{ studentsOnly: false }` to their Trip `where` clause for a non-student viewer (no filter at all for a student viewer, who sees everything) — same batched-query shape both pages already use, no per-card check.
  - **Direct access**: `/trips/[id]` calls `notFound()` for a non-student, non-owner viewer of a `studentsOnly` post — a 404, not a 403 or a "you can't see this" message, matching this app's existing don't-leak-existence idiom for private content (e.g. a `Conversation` a non-participant hits directly).
  - **Interaction entry points a non-student could otherwise reach directly** (bypassing Explore/Home and the detail-page gate): `POST /api/connection-requests` and `POST /api/conversations` each re-check `studentsOnly` against the caller and reject (403) if they're not a student — closing the gap for someone hitting these endpoints with a known id rather than discovering the post through the UI.
  - **Badges**: `ExploreCard` renders a "🎓 Students only" pill (`TripCardPost` carries `studentsOnly`, populated by Explore and Home's queries); the trip detail page shows the same label inline; `/my-posts` prefixes a 🎓 on the poster's own listing so they can tell at a glance which of their posts are gated.
  - **`GET /api/trips/[id]` / `GET /api/trips`**: require `getCurrentUser()` (401 otherwise) and apply the same `hasStudentRecord`-gated `studentsOnly` filtering every other surface uses (404-not-403 for the single-id route, matching the page route's own gate; `{ studentsOnly: false }` in the `where` clause for the list route, matching Explore/Home) — a lesson from a real earlier audit: "no UI consumes this yet" only justifies deferring a *feature*, never skipping *authorization* on a route that's already live.

## Home Page

`/` (`src/app/page.tsx`) is a **fork on `getCurrentUser()`**, not a single page: a signed-in visitor gets the narrow "surfaces the featured corridor prominently" glance view the plan doc describes; a logged-out visitor gets `LandingPage()`, an introduction/marketing page (hero tagline + subheading + "Get started free"/"Browse listings" CTAs, plus a small live preview grid of real listings) instead of being redirected to `/login`. This is a deliberate, explicit reversal of an earlier decision in this same file (Home used to `redirect("/login")` unconditionally, and this section used to say it "stays the one fully-gated page" specifically because `/explore`'s own logged-out preview didn't extend to it) — the product call changed to "a brand-new visitor's first page should be an introduction, not a login form," matching a reference marketing-page screenshot the same way `/explore`'s preview matched a reference browse-page screenshot. Styling is deliberately minimal for now (reuses `.explore-grid`/`ExploreCard` styling, a plain `<section>`/`<h1>`/`<h2>` structure) — this was built as the functional/structural version by explicit request, with visual polish deferred to a later pass.

### Signed-in view

- **`getFeaturedRoutePairs(user)`** (`src/lib/geo.ts`) resolves what region pair(s) to scope the feed to, returning `{ pairs: FeaturedRoutePair[], isPersonal: boolean }`. Tries the user's *personal* route first — the exact same derivation `getPrimaryRouteLabel` already uses (home region vs. university region, matched against an existing `RouteCommunity` row in either order) — and falls back to every currently-`active` `RouteCommunity` row (plural-safe: the schema has no constraint limiting "at most one active," even though seed data has exactly one) if no personal route is derivable (a parent, an alumni, or a student whose region pair has no `RouteCommunity` row at all). This is the **first code anywhere that actually reads `RouteCommunity.active`** — `getPrimaryRouteLabel` itself never checked it, since a personal route is valid regardless of whether its RouteCommunity happens to be flagged active or not. The two functions' personal-route condition deliberately stays duplicated rather than sharing a helper (different return shapes: a label string vs. queryable region ids+names) — each has a comment cross-referencing the other so they can't silently drift apart, since `/profile`'s displayed label and Home's actual feed scope must never visibly disagree for the same user. `getFeaturedRoutePairs` itself still requires a real `CurrentUser` (it reads `user.homeCity`/`user.studentRecord`) — a logged-out visitor's `LandingPage()` doesn't call it at all, since the "personal route" half is inapplicable with no account; it queries `active` `RouteCommunity` rows directly instead (the same fallback shape, simplified).
- **Query scoping**: an `OR`-of-both-directions filter (`originCity: { regionId: A }, destinationCity: { regionId: B }` or vice versa, flatMapped across every pair in scope) ANDs into Explore's existing `status`/`travelerId`/blocked-ids conditions — a cross-region match, not "touches this region at all," matching the "Bay Area ↔ UCI corridor" framing precisely. If no pairs resolve at all (no personal route, no active `RouteCommunity`), Home skips the Trip query entirely and shows a generic empty state rather than querying with no filter.
- **Heading** reflects which branch resolved: "Your route: X ↔ Y" when personal (identical label shape to `/profile`'s own `getPrimaryRouteLabel` string), "Featured route: X ↔ Y" when falling back to the active community.
- **Trip offers only**, same "package browsing is separate, out of scope" precedent Explore already set (see below) — not an oversight, and not new scope invented for Home. Weighted into 3 sections (📦 Package Deliveries / 🚕 Splitting an Uber/Lyft / 🚗 Individual Rides), each independently capped (`PACKAGE_PREVIEW_LIMIT`/`UBER_PREVIEW_LIMIT`/`TRIP_PREVIEW_LIMIT` in `src/app/page.tsx`) to carry a 50/30/10 visual-prominence split.

### Logged-out view (`LandingPage()`)

- **Same public-preview rules `/explore`'s logged-out mode already established**: trip offers only, `studentsOnly: false` (an anonymous visitor is never a student), no self-exclusion or blocked-user filtering (no viewer identity to exclude), `ExploreCard`'s `isLoggedIn={false}` prop so "Request to Connect" renders as a plain `<Link href="/sign-up">` instead of the real interactive button — see the Explore Page section below for the shared component contract.
- **Scoped to the active `RouteCommunity` only**, sorted the same date-ascending-with-nulls-last way the signed-in feed already sorts, same weighted 3-section split — deliberately a *preview*, not a full browse; `/explore` (linked from both the hero CTA and below the grid) is where a visitor goes to see everything. If no `RouteCommunity` is active, or the scoped query returns nothing, the grid is skipped in favor of a plain link to `/explore` rather than showing an empty grid.
- **Two CTAs in the hero**: "Get started free" → `/sign-up`, "Browse listings" → `/explore` — both reuse the existing `.connection-request-button` class for a consistent look with zero new CSS, consistent with "don't worry about UI right now."

## Explore Page

`/explore` (`src/app/explore/page.tsx`) browses upcoming Trip offer posts from **other** users — a server component querying Prisma directly, same convention as `/my-posts` and the trip detail page, not a client-side fetch against `/api/trips`.

- **Scope: Trip offers only** (both `personal_car` and `uber_share` categories — see the Trip Categories & Package Carrying section above). There is no standalone Request to merge in anymore (the "Need" flow that powered it was removed — see Trip Categories & Package Carrying above), and `PackagePost` rows aren't browsable here at all yet — package browsing would need its own dedicated page/card shape, not yet built.
- **Excludes the caller's own posts**: `travelerId: { not: user.id }`, mirroring the ownership pattern `/my-posts` and the detail page already use for edit/cancel permission checks.
- **Excludes anything not currently actionable**: DB-level `status: "upcoming"`, further filtered in application code through `tripDisplayStatus` (`src/lib/postStatus.ts`) so a past-due post that never got cancelled doesn't show as if it were still open — same derived-at-read-time helper `/my-posts` uses, nothing new persisted.
- **Filters** (`originCityId`, `destinationCityId`, `date`) live entirely in the URL's query params, not client state — the server component re-runs against the new query exactly as before, same as the Upcoming/History tabs on `/my-posts`. There is no Type filter — with only Trip offers left to browse, an offer-vs-request toggle has nothing left to discriminate. Two deliberate deviations from this otherwise-zero-JS page, both in `src/components/ExploreFilters.tsx` (a small Client Component): (1) the form auto-submits on any field's change event instead of requiring an explicit "Apply filters" click, via a single `onChange` on the `<form>` itself (catches every field through React's normal event bubbling, no per-field handlers or controlled state needed); (2) that submit is `router.replace(...)` (Next's client-side transition) built from the form's own `FormData`, not a native GET submit -- a native submit is a full browser navigation (page flash, full reload), which is exactly what auto-submit-on-every-keystroke-or-selection would make jarring. `replace()` rather than `push()` so adjusting filters doesn't pile up a back-button entry per change. `getCitiesByRegion()` (`src/lib/geo.ts`) populates the origin/destination pickers. **"Clear filters" also goes through `router.replace("/explore")`, never a plain `<Link>`** — a `<Link href="/explore">` was tried first and confirmed broken live: Next's viewport-prefetch can cache that URL's RSC payload while a filter was still active and reuse the stale, still-filtered render on click, so the address bar changed but the visible filter bar and results didn't. `router.replace()` (the exact call every other filter change here already uses) always goes through a real navigation instead. Separately, every field in this form is uncontrolled (`defaultValue`, not `value`) — React only applies `defaultValue` on a field's initial mount, so when the URL's filters change from *outside* this component's own `onChange` (a "Clear filters" click, or browser back/forward), an already-mounted `<select>`/`<input>` silently keeps showing its old selection even though the page's results correctly updated underneath it. The `<form>` is keyed on a string built from the current `originCityId`/`destinationCityId`/`date` (`formKey` in `ExploreFilters.tsx`) specifically to force React to remount it — and every uncontrolled field inside — whenever those values change for any reason, which is what actually resets the visible selections.
- **Route map** (`src/components/ExploreMapView.tsx` + `RouteMap.tsx`): a real interactive map (Leaflet + OpenStreetMap tiles + real geocoded coordinates, `leaflet`/`react-leaflet` npm packages) sitting alongside the results grid, highlighting the hovered card's route in solid blue against the rest in dashed gray. Chosen over the Google Maps JS API specifically to avoid Google's billing-account requirement (a Google Cloud project needs a card on file even for free-tier usage) — Leaflet+OSM needs no API key, no signup, no billing at all. `RouteMap.tsx` is a Client Component loaded via `next/dynamic({ ssr: false })` from `ExploreMapView.tsx`, since Leaflet touches `window`/`document` at module load and can't run during SSR; it draws city dots as `CircleMarker` (a plain SVG circle), not the default Leaflet pin `Marker`, deliberately sidestepping that pin icon's well-known bundler-asset-path breakage with webpack/Next.js. Hovering a card re-fits the map's viewport to just that route's two endpoints rather than always fitting every point on the page — necessary, not just polish: one geographically distant outlier elsewhere (a garbled destination Nominatim happened to match somewhere far away) would otherwise zoom the whole map out so far that a real, nearby hovered route shrinks to an invisible sliver.
  - **Standard OpenStreetMap raster tiles, muted via CSS** (`.route-map-tiles` in globals.css: grayscale + reduced saturation/contrast): a plain grid-canvas version (no tile imagery at all, just markers/lines on a flat background) was tried for one pass, per a reference "campus routes" mockup that itself had no real tile imagery — but live feedback on the actual result was that it read as "blank boxes," not an actual map, so real tiles are back. CARTO's free Positron tiles were tried once before *that* for the same clean-look goal and turned out to now require an API key, which is why this app mutes the standard always-free OSM tiles with a CSS filter instead of depending on another provider's basemap. The zoom `+`/`-` control and its restyled `.leaflet-control-zoom` chrome are back too (real map imagery benefits from an obvious way to zoom, unlike the flat-grid version). A `.schematic-map-eyebrow` "Campus Routes" label (reusing the app's own `.eyebrow` typography) still sits in the corner as a small white pill — necessary now, since plain floating text wouldn't stay legible over varied tile colors the way it did over a flat gray grid.
  - **Markers distinguish the hovered route's endpoints from ambient context**: every marker on the page renders as a small, flat gray dot with an always-visible (Leaflet `Tooltip permanent`, not hover-triggered) label by default (`.route-map-marker-dim` / `.route-map-marker-label`) — reading as ambient "other places nearby" context. The two endpoints of whichever route is currently hovered get a distinct, bolder treatment instead: a green-ringed white circle for the origin (`.route-map-marker-origin`) and a solid blue-filled circle for the destination (`.route-map-marker-destination`), each with a bold black label (`.route-map-marker-label-active`) and a subtle drop-shadow — computed by comparing each marker's coordinate-string key against the hovered post's own origin/destination keys (the same `lat.toFixed(4),lng.toFixed(4)` format the marker-dedup `Map` already keys on, so the two stay in sync for free). Every label (ambient or active) renders as a small white pill (`background: rgba(255,255,255,0.92)`), not plain text, so it stays legible regardless of what tile colors sit underneath it.
  - **Real coordinates, not the old hash-positioned placeholder**: `City.latitude`/`City.longitude` (nullable, migration `20260910193916_add_city_coordinates_and_geocode_cache`) are backfilled for the seeded cities in `prisma/seed.ts` and read directly when present (`getCityCoordinates`, `src/lib/geocode.ts`) — no network call. A write-in `destinationText` (e.g. "SFO Airport", no linked `City` row) or any `City` not yet backfilled falls back to `resolveCoordinates()`, which geocodes via OpenStreetMap's free Nominatim API and caches the result in the new `GeocodeCache` model (`query` -> lat/lng), keyed on the normalized (trimmed, lowercased) input text. Caching isn't just a performance nicety: Nominatim's public-instance usage policy caps requests at roughly 1/second and expects callers to cache results rather than re-resolving the same place repeatedly -- `resolveManyCoordinates()` resolves a batch of distinct names **sequentially**, not via `Promise.all`, for the same reason. `resolvePostCoordinates()` is the one entry point `/explore` (and any future caller) uses to batch-resolve a whole page of Trip rows at once. A place Nominatim can't find, or that a network failure prevents resolving, is simply **not plotted** on the map (`RouteMap.tsx` filters to only fully-coordinate posts) -- omitted, not guessed, same "don't fabricate incomplete data" precedent used elsewhere in this app (e.g. a card that can't compute a field just doesn't render it).
  - **Hovered route is bold and animated, not just recolored**: the hovered `Polyline` uses `weight: 5` (vs. `2` for every other route) plus a `.route-map-line-hovered` CSS `drop-shadow` glow, so it reads clearly against the map even when several routes are visually close together — the earlier version only changed color/opacity, which wasn't enough contrast once real (sometimes overlapping) geography was in play. `RouteMap.tsx`'s `FlowingDot` component also renders on top of the hovered route only: a small blue `CircleMarker` that travels from origin to destination and back on a 2600ms cosine-eased loop, animated by calling `.setLatLng()` on a ref inside a `requestAnimationFrame` loop rather than through React state/re-renders (smoother, and avoids re-rendering the whole map tree every frame). This is the literal "moving dot along a line" motif originally prototyped for the Home hero illustration and shelved there for lacking a real route to anchor to (see `HomeHeroIllustration`'s own comment in `src/app/page.tsx`) — it found its real home here, where a hovered post always has an actual origin/destination pair to travel between.
- **Card layout is ported pixel-for-pixel from a reference implementation**, not eyeballed from a screenshot: the user pointed this project at `C:\Users\sahil\Desktop\UI_Instructions`, a Figma Make export whose `src/App.tsx` contains a real `TripCard` component with exact colors/spacing/typography — after live feedback that an earlier pass's cards read as visibly squished (avatar and poster name cramped against the action button). `ExploreCard.tsx`'s values (10px radius, `18px 20px` padding, a default `0 1px 3px rgba(0,0,0,0.04)` shadow, `.explore-card-route-headline`'s 16px/800-weight/-0.025em city names with a small inline chevron SVG (`RouteArrow`) instead of a plain "→" character, `.explore-card-route-subtitle`'s 11.5px `--color-gray-meta`, the divider as a filled 1px `--color-gray-section` line rather than a border, `.explore-card-avatar`'s 34px size, etc.) are copied from that source, not approximated. The top-right seats badge (`seatsBadgeText()`) is uniformly neutral gray regardless of urgency, matching the reference exactly — a near-empty offer's urgency reads only through the amber (`#f59e0b`) " · Last seat" appended to the date line, the same place the reference puts it, not through the badge's own color. **Not** ported: the reference button's own "View trip" label/behavior (a plain nav link in that generic demo) — this app's real `ConnectionRequestButton` ("Request to Connect", opens a note composer) keeps its real label/behavior, only picking up the reference's tighter in-card sizing via a scoped override (`.explore-card-footer .connection-request-button`).
- **The poster stats line ("UC Irvine '26 · 11 trips") is real, computed data, not fabricated**: `PosterBadge` (`ExploreCard.tsx`) renders two rows: name + `Verified` badge on the first (matching the reference), then role (Student/Parent) + optional university/year + optional completed-trip count on the second, each `·`-joined segment appearing only when the underlying data exists — a caller with none of it (every other `PosterBadge` usage: `/connections`, `/trips/[id]`) still renders a clean single "Student"/"Parent" line, unchanged from before. `resolvePosterStats()` (`src/app/explore/page.tsx`) batches one `groupBy` query across every distinct poster on the current page (never per-card): completed `Trip` count by `travelerId`. There is no rating/star figure on this line — the `Review` model and the whole review feature were removed along with the standalone `Request` model they depended on (see Trip Categories & Package Carrying above); this line used to also show an average rating derived from `Review.rating`, which no longer exists. University name comes from `StudentRecord.universityDomain.universityName` (added to `posterSelect`'s `traveler` query); `shortenUniversityName()` collapses this app's one real seeded value, "University of California, Irvine", to "UC Irvine" for the compact card line (a targeted, common-abbreviation rule, not a guess) — any other university name would render unabbreviated. `formatYearLabel()` renders a 4-digit `User.year` as `'26`; since `year` is deliberately free text (see its schema comment), anything else ("Senior", "Junior") renders as-is rather than being mangled by an assumed format. `.explore-card-poster-role` wraps onto a second line (`flex-wrap: wrap`) rather than truncating with an ellipsis — this stats line exists specifically to fix a legibility complaint, so it must never silently cut itself off the same way.
- **`note` field** (`Trip.tripNotes`, wired through in `src/app/explore/page.tsx`) renders as an italicized quote at the very bottom of the card, above a thin top border, when present — omitted, not fabricated, when a post has none, same "don't invent missing data" precedent as everywhere else in this app.
- **Results sit inside a gray `.explore-panel` backdrop, widened site-wide**: `ExploreMapView.tsx` wraps the whole grid+map (`.explore-split`) in `.explore-panel` (`background: var(--color-gray-section)`, the same gray tone `.btn-secondary` already uses, padded and rounded) so the white cards and the white map both read as distinct "island" elements with real breathing room, rather than floating directly on the page's own white background — added after a live screenshot comparison against a reference mockup showed the difference plainly (mockup had generous, deliberate spacing; the unwrapped version looked cramped by comparison, even after `.site-main`'s max-width was widened, see below). `.schematic-map`'s own background changed from the same gray to `var(--color-white)` for the same reason — it needs to contrast against the new gray panel behind it, not blend into it. Card padding and grid gap both grew (`.explore-card` 1rem→1.5rem, `.explore-grid` gap 1rem→1.25rem, min card width `260px→340px` via `.explore-grid`'s `minmax()`) as part of the same "give it room to breathe" pass — the min-width bump in particular was a direct fix for the poster row: at the old 260px minimum, the avatar+name (`.explore-card-poster`, `flex: 1 1 auto` so it claims whatever space the fixed-width action button doesn't need) got squeezed enough that a real name could visibly truncate against the ellipsis in `.explore-card-poster-name`. The avatar itself also grew (`.explore-card-avatar` 36px→44px) to match. This is a container/spacing change only.
- **`.site-main`'s site-wide max-width was widened, `1280px → 1600px`** (`src/app/globals.css`): `.site-header` (the nav bar) has no max-width and spans the full viewport, so on a wide screen the previous 1280px cap on page content created a visible mismatch — a full-width header sitting above a narrow, centered content column with large unused margins on either side. Explore's own map column also grew (`.explore-split` `320px → 400px` wide, `.schematic-map` height `320px → 480px`) so it reads as a real panel rather than a cramped sidebar strip once the extra width was available. This is a genuine standing UI preference for this project (confirmed twice via direct user feedback), not just a one-off Explore tweak — default to using available viewport width rather than a conservative narrow max-width when building or reviewing other pages.
- **Results are paginated, `PAGE_SIZE = 4` per page**: the sorted Trip-offer feed is sliced in `src/app/explore/page.tsx` *before* any of the expensive per-post enrichment (connection-request status, confirmed-rider counts, coordinate resolution) runs, so browsing page 1 of a large result set never pays for work on posts that aren't even rendered yet. The current page comes from a plain `?page=` query param (clamped to `[1, totalPages]`, invalid/missing values fall back to page 1) — a server-rendered `<Link>` Previous/Next control (`.pagination-row` in `globals.css`) rebuilds the URL preserving the active `originCityId`/`destinationCityId`/`date` filters via a small local `pageHref()` helper, the same "plain query params, no client state" convention the filters themselves already established. No explicit reset-to-page-1 logic was needed when a filter changes: `ExploreFilters`' own `router.replace()` never includes `page` in the URL it builds, so changing any filter naturally drops back to an un-paginated `/explore?...` URL, which this page's own clamping already treats as page 1.
- **Loading/error states use Next.js App Router file conventions** (`src/app/explore/loading.tsx`, `src/app/explore/error.tsx`) rather than component-level state — the first file convention of this kind in the project; reach for the same pattern before inventing a bespoke spinner/error boundary elsewhere.
- **`src/components/ExploreCard.tsx`** renders one `TripCardPost` (the only post kind Explore browses now). The poster's Student/Parent status label is computed locally in that file from a minimal `{ signedUpAsParent, verifications }` shape selected directly on the query — **not** `universityBadgeLabel`/`parentRelationshipBadgeLabel` from `src/lib/auth.ts`, which require the full `CurrentUser` include shape (`parentLinksAsParent`, `homeCity`, `studentRecord`, …) that browsing another user's post has no reason to fetch.
- **Logged-out public preview** (added after launch, product decision): `/explore` and the trip detail page it links to (`/trips/[id]`) are the **one** deliberate exception to "every page requires login" — `getCurrentUser()` is called but its `null` result is **branched on, never redirected** (the same shape `/family/invite/accept` already used for a different reason — see that section above). A logged-out visitor sees the exact same listing data a real non-student user would (`studentsOnly` posts excluded via the same `{ studentsOnly: false }` filter, `hasStudentRecord` guarded as `user ? hasStudentRecord(user) : false` since that helper itself still requires a real `CurrentUser` and was deliberately left untouched), and a `studentsOnly` post's detail page still 404s for them, not a special "log in" message — same don't-leak-existence idiom as every other non-entitled viewer. What's **withheld**: `ReportButton`/`BlockButton` (both inherently require an account, so they're simply absent, not sign-up links — there's no useful "preview" of reporting or blocking someone), and every real interaction control (`ConnectionRequestButton`, `RegisterInterestForm`) — each is swapped for a plain `<Link href="/sign-up">` carrying the **same button label** ("Request to Connect", "Register for a seat"), so clicking the action itself is what sends a visitor to sign up, per product decision, rather than an inline "please log in" prompt first. `/` (Home) later got the equivalent treatment too, once it stopped redirecting logged-out visitors — see its own section above. The interaction API routes themselves needed **zero changes**: `POST /api/connection-requests`, `POST /api/conversations`, etc. already 401'd with no session before this, so this whole feature is page-level rendering only, not new security surface.

## Messaging

Implements the `Conversation`/`Message` module the plan doc (§11) describes: "a prospective requester can message the traveler with questions *before* committing to a formal request" — `Conversation` stays scoped to `(tripId, counterpart)` (or `packagePostId`, see Trip Categories & Package Carrying above). This module itself deliberately does **not** create a `ConnectionRequest` or touch `Trip.seatsRemaining` directly — don't let "register for a seat" as a button label imply a real reservation exists yet. (Trip Participants and Seat Offers, both below, are separate mechanisms that *do* eventually touch `seatsRemaining`; Seat Offers in particular is reached from within a `Conversation` created by this module, but the two remain distinct systems.)

- **Entry point**: `RegisterInterestForm` (`src/components/RegisterInterestForm.tsx`) on `/trips/[id]`, shown to non-owner viewers only when the trip is actionable (`tripDisplayStatus(trip) === "upcoming"`) and `seatsRemaining > 0`. Clicking "Register for a seat" reveals a message composer (prefilled, editable) rather than firing silently — the button *prompts* a message, it doesn't send a canned one unseen.
- **`POST /api/conversations`** (`src/app/api/conversations/route.ts`, previously nonexistent — the API module listing below only had `[id]/messages`) takes `{ tripId, body }` **or** `{ packagePostId, body }` (a Zod schema with both fields optional, validated as "at least one present" in the route body rather than a `z.union`, since the two branches share the identical `body` field and mostly-parallel validation), finds-or-creates a `Conversation` for the given post + the caller + the post's owner (`trip.travelerId` or `packagePost.postedById`), and creates `body` as the first `Message`. Rejects messaging your own post and messaging a non-upcoming trip / non-open package post server-side, not just via the UI gate above. The find-or-create is a plain find-then-create, **not** the race-hardened pattern `claimOrCreateStudentRecord` uses for `StudentRecord` — a duplicate thread here is a minor UX nuisance, not a security or data-integrity issue, so that extra rigor isn't worth it here.
- **`GET /api/conversations`** lists the caller's threads (most recent first) for `/messages`; **`GET /api/conversations/[id]`** and **`GET`/`POST /api/conversations/[id]/messages`** (the latter two previously `501` stubs, now implemented) all 404 — not 403 — when the caller isn't a `ConversationParticipant`, so a thread's existence isn't leaked to someone outside it. The participant check is a small local (non-exported) helper duplicated across these files rather than pulled into a shared lib module — each file's route export validation only allows HTTP-method exports, and the check is a few lines, not worth a new module for.
- **Polling, not websockets/realtime** (plan doc §14): `MessageThread` (`src/components/MessageThread.tsx`), the client component behind `/messages/[id]`, re-fetches `GET .../messages?since=<lastMessageTimestamp>` every 4s while the thread is mounted. `since` is always a pre-serialized ISO string on both the initial server-rendered messages and every polled batch, so the component's `Message` type never has to reconcile a `Date` object from one path against a JSON string from the other.
- **Rate limited**: `canSendMessage(userId)` (`src/lib/rate-limit.ts`, same rolling-window-count shape as `canCreatePost`) caps a user at 30 messages per rolling 10-minute window, checked in both `POST /api/conversations` and `POST /api/conversations/[id]/messages` (429 if exceeded) — added after a security audit flagged that a scripted loop could otherwise flood a specific victim's thread with unlimited messages, a direct harassment vector. Global per-sender across all their conversations, not per-thread, mirroring `canCreatePost`'s own global-per-user shape.
- **Unread indicators**: `ConversationParticipant.lastReadAt` (nullable `DateTime`, migration `20260819021514_add_conversation_participant_last_read_at`) records when each participant last opened a thread. `src/lib/messaging.ts`'s `isConversationUnread` is the single unread rule (latest message from the other party, and either never-opened or that message postdates `lastReadAt`) — shared by `/messages` (bold title + "New" badge per row) and the nav's "Messages" item (`src/app/layout.tsx`, red count badge via `getUnreadConversationCount`, also in `src/lib/messaging.ts`). `MessageThread` calls **`POST /api/conversations/[id]/read`** on mount and after every poll that brings in new messages, so opening a thread — or leaving it open while a reply arrives — keeps it marked read. That route's `updateMany` on `(conversationId, userId)` doubles as its own authorization check (0 rows updated → 404), the same "don't leak conversation existence" pattern as the other `/api/conversations/[id]*` routes.
- **`findOrCreateConversationForPost(tripId, userIdA, userIdB)`** (`src/lib/messaging.ts`) is the one conversation-creation code path in the app — extracted from `POST /api/conversations` so `POST /api/connection-requests/[id]/accept` (see Connection Requests below) can reuse it exactly rather than standing up a second way to create a `Conversation`.
- **Archive/Delete + last-activity timestamp** (migration `20260828172647_add_conversation_archive_delete`): `/messages` now shows each row's last-activity time (`lastMessage?.sentAt ?? conversation.createdAt`, same `.message-meta` timestamp styling used inside the thread) and a per-row `ConversationActions` control (`src/components/ConversationActions.tsx`). Both new fields live on `ConversationParticipant`, not `Conversation` — this is a **per-user view preference**, never a shared/destructive action: one participant hiding a thread never touches the Conversation/Message rows themselves or the other participant's own view, same "don't delete shared history" precedent as Trip cancellation leaving `ConnectionRequest`/`Conversation` rows untouched.
  - **`archivedAt`**: `POST /api/conversations/[id]/archive` / `.../unarchive`. Sticky — a new message does **not** auto-clear it, the user has to explicitly unarchive. `/messages` gets an Inbox/Archived `?tab=` split (same zero-JS query-param convention as `/my-posts`/`/connections`); `getUnreadConversationCount` (nav badge) excludes archived conversations, since the badge's purpose is prompting a check of the main inbox.
  - **`deletedAt`**: `DELETE /api/conversations/[id]` (confirm()-gated in the UI). Hides the thread from **both** tabs entirely — there's no separate "trash" view. Unlike `archivedAt`, this **is** auto-cleared the moment either party sends a new message, so a deleted thread resurfaces on new activity instead of silently going unnoticed forever: `findOrCreateConversationForPost` clears it when *reusing* an existing conversation (covers the "connect again after accepting/registering interest" path, since both of its callers create their own first `Message` directly rather than going through the messages route), and `POST /api/conversations/[id]/messages` clears it independently for the ongoing-chat case that never calls `findOrCreateConversationForPost` at all. Both routes use the same `updateMany`-as-authz idiom as `POST /api/conversations/[id]/read`.

## Connection Requests

A formal, gated request-to-connect lifecycle (`ConnectionRequest` model: `pending` → `accepted`/`declined`/`cancelled`) layered **on top of**, not instead of, the ungated Messaging flow above — RegisterInterestForm's "message the traveler immediately, no approval needed" behavior is untouched. The two are genuinely different products: RegisterInterestForm is "ask a quick question," ConnectionRequest is "ask the trip owner's explicit permission before a thread exists." Both end up at the exact same place once a connection exists — a `Conversation` via `findOrCreateConversationForPost` — so accepting a `ConnectionRequest` and clicking "Register for a seat" on the same trip pair converge onto one thread, not two.

- **Where the button lives**: `ConnectionRequestButton` (`src/components/ConnectionRequestButton.tsx`) appears in two places for the same reason RegisterInterestForm only appears once — non-owner viewers of an *upcoming* trip: `/trips/[id]` (via a server-fetched `myConnectionRequest`/`acceptedConversation` lookup) and every offer `ExploreCard` (via a single batched query in `/explore/page.tsx`, not one query per card). The button only reflects whether there's a **live** (pending/accepted) request — a declined or cancelled one reverts it to a plain, clickable "Request to Connect" again, since only a *pending* duplicate is blocked (see the schema comment on `ConnectionRequest`). The historical declined/cancelled record is what `/connections`'s Sent tab is for, not this button.
- **`ExploreCard` restructuring**: the card is now a `<div>` wrapping an inner `<Link>` (renamed `.explore-card-link`) plus a sibling `.explore-card-actions` region for the button — previously the whole card *was* the `<Link>`. This was a required, not cosmetic, change: HTML disallows interactive content (a `<button>`) inside an `<a>`, and nesting them would make clicks ambiguous anyway. `PosterBadge` (the avatar/name/role block) is now exported from this file and reused by `/connections` for "Requester's name, Profile picture, Student/parent status" rather than re-implementing that block a third time.
- **`POST /api/connection-requests`** (body `{ tripId }`) always derives `requesterId` from the authenticated caller and `recipientId` from `trip.travelerId` — neither is ever read from the request body, which is what actually prevents "create a request pretending to be someone else," not a check that could be bypassed. Rejects your own trip, a non-upcoming trip (same `tripDisplayStatus` gate `POST /api/conversations` uses), and a duplicate *pending* request (409) via a plain find-then-create — same "minor UX nuisance, not worth race-hardening" calibration as `findOrCreateConversationForPost`.
- **`POST /api/connection-requests/[id]/{accept,decline,cancel}`**: accept/decline require `recipientId === caller` (403 otherwise); cancel requires `requesterId === caller` (403 otherwise) — the inverse ownership check on purpose, since only the requester should be able to withdraw their own ask. All three require `status === "pending"` first (400 "already resolved" otherwise) — there is no un-declining or re-accepting a resolved request. These three use 403 for a wrong-caller mismatch, not the 404-to-avoid-leaking-existence pattern the private `Conversation` thread routes use — `ConnectionRequest` ownership checks are conceptually closer to the existing `Trip`/`Request` ownership checks (which are already 403 elsewhere in this codebase) than to a DM thread's privacy model. Only `accept` touches `Conversation`, via `findOrCreateConversationForPost`; `decline` and `cancel` never create one.
- **`/connections`** (Received default, `?tab=sent`) follows the exact `/my-posts` Upcoming/History convention — plain query param, server-rendered, no client JS for the tab switch. Pending rows get `RespondToConnectionRequestButtons` (Accept/Decline, Received tab only) or `CancelConnectionRequestButton` (Sent tab only). Decline and Cancel follow `DeletePostButton`'s confirm-then-fetch-then-`router.refresh()` shape; **Accept does not** — it `router.push()`es straight to `/messages/[conversationId]` (the id `POST .../accept` already returns) instead of staying on `/connections`, since the whole point of accepting is to land in the resulting chat.
- **No DB-level uniqueness on `(tripId, requesterId)`** — see the long comment on the `ConnectionRequest` model in `prisma/schema.prisma` before adding one; a blanket unique constraint would block the intentional "try again after a decline" flow.
- **Required note (`ConnectionRequest.message`, migration `20260820170907_add_connection_request_message`)**: clicking "Request to Connect" reveals a composer (`ConnectionRequestButton`'s `composing` state) with a **required** textarea, labeled "Tell the trip owner why you're connecting" — same reveal-on-click shape as `RegisterInterestForm`, but a plain one-click request with no context is no longer possible; both the client (`disabled={loading || !message.trim()}`) and `POST /api/connection-requests` (Zod `.min(1, ...)`) enforce this, the DB column itself stays nullable only because it postdates this model's earliest rows (same convention as `Trip.title`). `POST /api/connection-requests` folds a truncated preview into the `connection_request` notification text. `/connections` renders it (both tabs) as an italicized `.connection-item-message` line under the status, so the trip owner has context *before* deciding — this is the primary point of the field. If the request is later accepted, `POST /api/connection-requests/[id]/accept` seeds the same text as the first `Message` in the resulting `Conversation` (sender = the requester), so the context carries into the chat too rather than being stranded on a row the requester can no longer act on.

## Notifications

An in-app `Notification` model (`prisma/schema.prisma`), one row per event, read by the caller only — no push/email/SMS delivery. `src/lib/notifications.ts`'s `createNotification()` is the single creation path (same "one function, every trigger site calls it" convention as `findOrCreateConversationForPost`), called from exactly four places today: `POST /api/connection-requests` (notifies the trip owner), `POST /api/connection-requests/[id]/accept` and `.../decline` (both notify the original requester), and the two message-creation routes (`POST /api/conversations` and `POST /api/conversations/[id]/messages`, both notify the other conversation participant(s), never the sender). Each of those events is naturally non-duplicating: connection-request creation is already blocked from duplicating by the existing pending-request check, accept/decline can each only fire once per request (`status !== "pending"` guard), and a message notification corresponds 1:1 with an actual new `Message` row.

- **Fields**: `type` (`connection_request` | `connection_accepted` | `connection_declined` | `new_message`), `title`, `message` (both plain strings written at creation time, not re-derived at read time — a notification still reads correctly even after the thing it points at changes state further), `relatedId` (untyped, points at whichever entity `type` implies — a `ConnectionRequest` or a `Conversation`, never a second FK per possible target), `isRead`, `createdAt`.
- **Where a click goes**: `notificationLink()` (`src/lib/notifications.ts`) is the one type→URL mapping. `connection_request` → `/connections` (Received tab, the default); `connection_declined` → `/connections?tab=sent`; `connection_accepted`/`new_message` → `/messages/[relatedId]` (the conversation thread). The first two don't deep-link to a single row because a connection request can be re-sent after a decline, so there's no permanently stable target to point at.
- **`/notifications`**: a server component querying Prisma directly (same convention as `/messages`/`/connections`, not a client fetch against a GET listing route — there is no `GET /api/notifications`), most recent first, capped at 100 rows (a simple cap, not real pagination, consistent with the rest of the app). Has `loading.tsx`/`error.tsx` following the Explore page's App Router file-convention pattern. Each row is `NotificationItem` (`src/components/NotificationItem.tsx`, client component): the whole row is a `Link` to `notificationLink()`'s target, and clicking it fires a fire-and-forget `POST /api/notifications/[id]/read` (same pattern `MessageThread` uses for its own read receipts) before letting navigation proceed — no `preventDefault`, so Next's `Link` still navigates normally. A separate small "Mark as read" button covers marking a notification read without leaving the page. `MarkAllNotificationsReadButton` posts to `POST /api/notifications/read-all`.
- **Security**: `POST /api/notifications/[id]/read` uses the same `updateMany(WHERE id, userId)`-doubles-as-authorization pattern as `POST /api/conversations/[id]/read` — 0 rows affected (wrong owner or nonexistent id) returns a 404, no distinction leaked. `POST /api/notifications/read-all` scopes its `updateMany` to `WHERE userId = caller`, so it can only ever touch the caller's own rows — there's no id parameter for another user's id to leak into.
- **Nav bell**: `layout.tsx` adds a "🔔 Alerts" item to `NAV_ITEMS`, badge-count computed via `getUnreadNotificationCount()` (`src/lib/notifications.ts`) the same way the existing "Messages" badge already works — computed fresh on every full server render, not client-polled. Deliberately a separate count from the Messages unread-conversation count, not merged into one total: an accepted/declined connection request has no corresponding "unread conversation" at all, so folding them together would either double-count message notifications or silently drop connection-request ones from the badge. Like the Messages badge, this only recomputes on a full page load/server render — a client-side `<Link>` navigation that stays under the same root layout won't refresh it immediately, the same already-documented Next.js App Router caveat noted under Auth Architecture for the parent-link gate.

## Trip Management (Trip Lifecycle)

A `Trip` moves through a real three-stage lifecycle -- `upcoming` → `completed` | `cancelled` -- with the owner-facing actions (Edit, Cancel, Mark Completed) that make those transitions reachable.

- **`TripStatus.active` was renamed to `upcoming`** (migration `20260820051301_trip_lifecycle_and_cancel_notification`, a real Postgres `ALTER TYPE ... RENAME VALUE` -- a metadata-only change, so the two rows that already existed under `active` came along automatically with no data rewrite and no need to backfill). Every prior `status: "active"` / `tripDisplayStatus(trip) === "active"` comparison in the codebase (Explore's query, `POST /api/trips`, `POST /api/connection-requests`, `POST /api/conversations`, the trip detail page, `postStatus.ts`) was updated to `"upcoming"` in the same pass. Do this kind of rename sparingly -- it was judged worth it here specifically because the mismatch between "active" (implies presently happening) and what the value actually means (not yet departed, still actionable) was a real, recurring point of confusion once a genuine 3-stage lifecycle existed to name precisely, and the blast radius was small (six call sites) and mechanically safe (`RENAME VALUE`, not a drop-and-recreate).
- **Edit** (`PATCH /api/trips/[id]`, `/trips/[id]/edit`): only reachable while `trip.status === "upcoming"` -- enforced in the route (400 otherwise) and in the edit page itself (redirects back to the detail page for a non-upcoming trip), not just by hiding the Edit link. No clear product reason surfaced for allowing edits on a completed/cancelled trip, so it's fully blocked rather than half-allowed.
- **Cancel** (`DELETE /api/trips/[id]`, `DeletePostButton` with trip-specific `actionLabel`/`confirmMessage` props): only reachable from `upcoming`. Confirmation is the existing `confirm()` dialog `DeletePostButton` also uses for `PackagePost` cancel, just with trip-specific copy that mentions connected users get notified. Cancelling:
  1. Sets `Trip.status = "cancelled"` and, in the same `$transaction`, bulk-flips every **pending** `ConnectionRequest` on that trip to `status = "cancelled"` too -- reusing the existing status value a requester's own `/cancel` already produces (from the requester's side, "my request is cancelled" reads correctly regardless of who triggered it), rather than inventing a new `ConnectionRequestStatus`.
  2. Leaves every **accepted** `ConnectionRequest` completely untouched -- status stays `accepted`, its `Conversation` stays fully intact and browsable. Per product decision, cancelling the trip never deletes or hides historical connection data.
  3. Notifies every affected requester (pending or accepted) via the one notification path (`createNotification`, see Notifications above) with a new `trip_cancelled` `NotificationType` -- wording differs by case ("your request has been cancelled" vs. "your conversation is still available"), but both link to `/connections?tab=sent` (`notificationLink()` in `src/lib/notifications.ts`), since that tab already shows the right status and links into the trip either way.
- **Mark Completed** (`POST /api/trips/[id]/complete`, `MarkTripCompleteButton.tsx`): only reachable from `upcoming`, owner-only, `confirm()`-gated -- the owner declaring their own Trip done, no counterpart negotiation. Deliberately does **not** touch any `ConnectionRequest` on the trip -- per product decision, existing connections (pending or accepted) remain exactly as they were. The one thing that does change as a result: `POST /api/connection-requests/[id]/accept` now re-checks `tripDisplayStatus(connectionRequest.trip) === "upcoming"` before accepting (400 otherwise) -- this is what actually prevents a stale pending request from being accepted against a trip that's already completed (or cancelled, though a cancelled trip's pending requests are already flipped away from `"pending"` by step 1 above, so this check mostly matters for the completed case).
- **Trip detail page (`/trips/[id]`)**: owner actions (Edit · Mark Completed · Cancel Trip) show only while `isUpcoming`. For non-owners, an **already-accepted** connection keeps showing its "Connected — View messages" state even after the trip stops being upcoming (`connectionRequestStatus === "accepted" || isUpcoming` gates the `ConnectionRequestButton`) -- only a *fresh* request is blocked once the trip isn't upcoming, not the visibility of an existing one. A non-owner with no accepted connection sees a plain "This trip is no longer accepting connections." message instead of the request/register-interest controls silently vanishing.
- **`/my-posts`**: what counts as "Upcoming" for **Trips** is `tripDisplayStatus(trip) === "upcoming"`, not a pure date split -- a cancelled-but-future-dated trip used to sit under Upcoming with just an inline "(cancelled)" label, which is exactly the muddled experience this feature was asked to fix. The History tab now sub-groups Trips under **Completed**, **Cancelled**, and (only if any exist) **Past due** headings — the last one covers a trip whose DB status is still `upcoming` but whose date has passed without the owner marking it completed or cancelled (`tripDisplayStatus` returns `"expired"` for these); Past-due trips still show the full Edit/Mark Completed/Cancel action row (nudging the owner to resolve them), since they're still `status: "upcoming"` under the hood. Each Trip row also shows a cheap connection-request summary ("3 connection requests (1 accepted)"), computed via one `groupBy` query across all the caller's trips rather than per-row — this is what satisfies "show relevant trip and connection information" for Completed trips without building any new feature.
- **Explore integration required no new filtering logic** — `/explore` and `GET /api/trips` already filtered on `status: "upcoming"` (formerly `"active"`) at the DB level plus `tripDisplayStatus(trip) === "upcoming"` in application code; once Cancel/Complete can actually change a Trip's status, those existing filters do the rest. Same for the "prevent new connection requests to an inactive trip" requirement — `POST /api/connection-requests` and `POST /api/conversations` already rejected a non-upcoming trip server-side from when Explore was first built.
- **Security**: every new/changed route (`PATCH`, `DELETE`, `POST .../complete` on `/api/trips/[id]`) follows the exact existing pattern — `getCurrentUser()`, then `trip.travelerId !== user.id` → 403, then a `trip.status !== "upcoming"` check → 400 — enforced server-side regardless of what the UI shows or hides. These application-code checks are still the only *authorization* enforcement in this project — RLS is enabled but policy-free and unrelated to this (see the Architecture Summary's design-principles list), same as everywhere else (see Trip Posting System above).

## Trip Participants (Seat Confirmation)

Lets a Trip owner turn an accepted `ConnectionRequest` into an actual confirmed seat, decrementing `Trip.seatsRemaining` — the first real write path for that field other than the create/edit "reset to seatsTotal" paths (see Trip Posting System above). Seat confirmation answers the question "of the people I'm already connected with about this specific trip, who's actually riding" — using data that already exists (everyone here went through Request to Connect → Accept first) and needing no new "search for a user to add" surface, which this app deliberately doesn't have (no public user directory, see Profile & Onboarding above).

- **Schema**: `ConnectionRequest.seatConfirmedAt` (nullable `DateTime`, migration `20260820215259_trip_participants_seat_confirmation`) is set/cleared only ever inside the same DB transaction as an opposite decrement/increment of `Trip.seatsRemaining` — the two fields have no other way to stay in sync, since `seatsRemaining` doesn't otherwise derive from anything. Distinct from `status` itself: not every accepted connection becomes a rider (a chat that fell through, or a package-only connection), so `status = accepted` alone doesn't imply a seat is held.
- **`POST /api/connection-requests/[id]/confirm-seat`**: owner-only (`recipientId === caller`, 403 otherwise), requires `status === "accepted"` and `seatConfirmedAt` still null (400 otherwise), and requires `tripDisplayStatus(trip) === "upcoming"` (400 otherwise — same gate `accept`/`POST /api/conversations` already use). The capacity check and decrement run inside one interactive `$transaction`: `Trip.seatsRemaining` is decremented via an `updateMany` guarded on `seatsRemaining: { gt: 0 }` (the same "0 rows affected" idiom already used for `POST /api/conversations/[id]/read` and `POST /api/notifications/[id]/read`, here repurposed as a concurrency guard rather than an authorization check) — if that affects zero rows, the whole transaction throws and nothing is written, including `ConnectionRequest.seatConfirmedAt`. This is exactly the "capacity check + decrement inside a single DB transaction to prevent overbooking races" the old `requests/[id]/accept` `TODO` comment called for, just applied to this narrower feature. On success, notifies the requester (`trip_seat_confirmed` `NotificationType`, links to `/trips/[id]` via `notificationLink()` — the only notification type whose `relatedId` is the trip's own id rather than a `ConnectionRequest`/`Conversation` id, since the rider's own status is already visible right there on the trip detail page).
- **`POST /api/connection-requests/[id]/release-seat`**: owner-only, requires `seatConfirmedAt` already set (400 otherwise). Undoes a confirm-seat mistake — clears `seatConfirmedAt` and increments `seatsRemaining` back, in one transaction. Deliberately has **no** upcoming-only restriction (unlike confirm-seat) and sends **no** notification — this is a correction of the owner's own bookkeeping, not a new user-facing event, same product judgment as Mark Completed not touching `ConnectionRequest` at all.
- **Trip detail page (`/trips/[id]`)**: owners see a "Participants" section listing every accepted `ConnectionRequest` **and** every accepted `SeatOffer` for the trip (see Seat Offers below — the two mechanisms are merged into one roster, since from the owner's point of view it's just "who's riding"), `PosterBadge`-rendered (reused from Explore/`/connections`), each with `ConfirmSeatButton` (`src/components/ConfirmSeatButton.tsx` — generalized via an `id`/`kind` prop pair rather than a `ConnectionRequest`-specific one, toggles between "Add as Participant" and "✓ Confirmed · Remove", same confirm-then-fetch-then-`router.refresh()` shape as `MarkTripCompleteButton`, `confirm()`-gated only on the Remove path; a `SeatOffer` row is only ever rendered already-confirmed, so "Add as Participant" is unreachable for that kind). Shown regardless of trip status, not just `isUpcoming`, so a completed/cancelled trip's participant history stays visible and correctable — only "Add as Participant" itself is upcoming-gated (disabled once `seatsRemaining` hits 0, hidden entirely once the trip isn't upcoming and the connection was never confirmed, since confirm-seat would 400 either way). A confirmed rider sees their own "✓ You have a confirmed seat on this trip." note next to their `ConnectionRequestButton` — `RegisterInterestForm`'s "Register for a seat" button (the ungated ask-a-question flow, see Messaging above) still shows alongside it whenever seats remain, since the two flows remain genuinely independent.
- **Trip edit (`PATCH /api/trips/[id]`) had to change**: it used to unconditionally reset `seatsRemaining` to the new `seatsTotal`, correct only because "nothing can have booked a seat yet" — no longer true once this feature exists. It now computes a consumed-seats total via `getConfirmedRiderCounts` (`src/lib/tripParticipants.ts` — `ConnectionRequest.seatConfirmedAt` + `SeatOffer.seatConfirmedAt`, every mechanism that can hold a seat, see the Seat Offers section) and sets `seatsRemaining = seatsTotal - totalConsumed`, rejecting the edit outright (400, not silently clamped) if the new `seatsTotal` would go below the already-consumed total — there's no correct number to fall back to in that case; the owner has to release a seat first.
- **Security**: both new routes follow the exact existing `getCurrentUser()` → ownership check (403) → status check (400) pattern used everywhere else in this file; RLS plays no role in this (see the Architecture Summary's design-principles list), same as always.
- **One rider, at most one confirmed seat per trip, enforced across both mechanisms**: `hasConfirmedSeatOnTrip(tripId, userId)` (`src/lib/tripParticipants.ts`) checks both `ConnectionRequest.seatConfirmedAt` and `SeatOffer.seatConfirmedAt` for that user on that trip, and gates every place a seat can newly become confirmed for someone — `POST /api/connection-requests/[id]/confirm-seat` (blocks confirming a second accepted `ConnectionRequest` from someone already riding, whether via an earlier `ConnectionRequest` or a `SeatOffer`), `POST /api/seat-offers/[id]/accept` (same, from the recipient's side), and `POST /api/seat-offers` creation (early rejection so the owner doesn't even send a redundant offer to someone already confirmed, though the real enforcement is at accept time since the recipient could still become confirmed elsewhere in between). A plain pre-check, not a serializable transaction — same "not worth race-hardening beyond the existing guarded-decrement idiom" calibration as the duplicate-pending-request checks elsewhere in this file; the `seatsRemaining` capacity guard itself (unaffected by this check) still guarantees the trip is never oversold even in the rare case two simultaneous confirms for the same rider both pass this check.
- **Confirmed riders are public, not owner-only** (per product decision): `/trips/[id]` shows a read-only "Riders" section to **non-owner** viewers listing everyone with a confirmed seat (`confirmedRiders`, the `seatConfirmedAt`-filtered subset of the owner's own `participantRows` — deliberately narrower than what the owner sees, since the owner's full list also includes accepted-but-not-yet-confirmed `ConnectionRequest` candidates, an in-progress management detail that stays private). No management buttons on this public view, just `PosterBadge` per rider. The same count also surfaces compactly on `/explore` and Home cards via `ExploreCardPost.confirmedRiderCount` ("🎫 N confirmed riders", shown only when `> 0`) — computed batched across every card via `getConfirmedRiderCounts(tripIds)` (`src/lib/tripParticipants.ts`, the same helper `PATCH /api/trips/[id]` uses for its own single-trip count), so browsing either page never does a per-card query.

## Seat Offers

The owner-initiated counterpart to Trip Participants above: a trip owner can offer a seat directly to someone they're already messaging (e.g. via `RegisterInterestForm`'s ungated "Register for a seat" DM), not just people who've gone through the requester-initiated Request to Connect flow. Before this, someone who only DMed the owner had no path at all into the Participants roster — that list only ever pulled from accepted `ConnectionRequest`s.

- **`SeatOffer` model** (migrations `20260828165939_add_seat_offers` + `20260828170524_add_seat_offer_trip_cancelled_notification_type`): `tripId`, `recipientId`, `conversationId` (always sent from within an existing `Conversation` — there's no other UI surface to reach this from), `status` (`pending → accepted/declined/cancelled`), `seatConfirmedAt` (kept separate from `status`, same convention as `ConnectionRequest.seatConfirmedAt`, so a later "Remove" doesn't erase the historical fact that the recipient accepted). Deliberately **not** built by reusing `ConnectionRequest` with a reversed direction — that model's `recipientId = trip owner` invariant is load-bearing across many existing routes (ownership checks on accept/decline/confirm-seat/release-seat, the `/connections` Sent/Received tabs); inverting it for an owner-initiated case would corrupt that rather than simplify anything. No DB-level uniqueness on `(tripId, recipientId)`, same "only a pending duplicate blocks a fresh attempt" tradeoff as `ConnectionRequest`.
- **`POST /api/seat-offers`** (body `{ conversationId }`): caller must be that conversation's trip owner (403 otherwise); `recipientId` is derived from the conversation's own participants (the other one), never trusted from the body. Rejects a non-upcoming trip, zero seats remaining, a block between the two parties (same check `POST /api/conversations`/`POST /api/connection-requests` already use), and a duplicate pending offer to the same recipient (409).
- **`POST /api/seat-offers/[id]/accept`**: caller must be `recipientId`. Unlike `ConnectionRequest` (accept, then a *separate* owner "Add as Participant" step via `confirm-seat`), accepting a `SeatOffer` **is** the seat confirmation — the offer already represents the owner's specific one-seat commitment, so accept atomically decrements `Trip.seatsRemaining` in the same transaction as the status flip, same guarded-`updateMany`-as-concurrency-guard idiom as `confirm-seat`.
- **`POST /api/seat-offers/[id]/decline`**: caller must be `recipientId`. No capacity change. **`POST /api/seat-offers/[id]/cancel`**: caller must be the trip owner rescinding their own still-pending offer (the inverse ownership check from accept/decline) — no notification, matching `ConnectionRequest` cancel's own precedent. **`POST /api/seat-offers/[id]/release-seat`**: caller must be the trip owner; mirrors `ConnectionRequest`'s own release-seat exactly (clears `seatConfirmedAt`, increments `seatsRemaining` back, `status` stays `accepted` as history, no upcoming-only restriction, no notification).
- **Three new `NotificationType` values** (`seat_offer_received`, `seat_offer_accepted`, `seat_offer_declined`) plus a fourth for trip cancellation (`seat_offer_trip_cancelled`, kept distinct from `trip_cancelled` since that type's `relatedId` is always a `ConnectionRequest.id`, hardcoded to `/connections` in `notificationLink()` — wrong for a `SeatOffer`, whose `relatedId` is a `Conversation.id`).
- **UI is an inline bubble inside the message thread itself, not a separate control above it** (per product decision, refined after the first pass): `SeatOfferBubble` (`src/components/SeatOfferBubble.tsx`) renders one `SeatOffer` as a chat-bubble-styled `<li>` inside `MessageThread`'s own `<ul className="message-thread">`, positioned chronologically among real `Message`s by `createdAt` (a unified, sorted `items` array built in `MessageThread`, not two separate lists) — its Accept/Decline (recipient, while pending)/Cancel (owner, while pending)/Remove (owner, once accepted) controls are clickable elements inside the bubble itself, and every bubble carries a timestamp via the same `.message-meta` styling real messages use, so the thread reads as one consistent, fully-timestamped stream. The owner's "Send Seat Request" trigger lives just above the compose box, only shown when there's no currently pending/accepted offer already (the active offer's own bubble already carries the relevant action). `GET /api/conversations/[id]/messages` (the existing 4s poll endpoint) now also returns the conversation's full current `seatOffers` list on every tick — not `since`-filtered like messages, since an accept/decline/cancel is an UPDATE that doesn't change `createdAt` — so an offer's status updates live for both parties without a page reload, the same as new messages already do. `MessageThread` owns `seatOffers` as local state (`useState(initialSeatOffers)`, updated via a `patch`-based `onUpdate` callback the bubble calls after each successful action, or wholesale-replaced by the poller), the same pattern `messages` state already used — this replaced the original design's separate `SeatOfferButton`/`RespondToSeatOfferButtons` components entirely (deleted), which lived above the thread and didn't sync live. On `/trips/[id]`, accepted `SeatOffer`s are still merged into the same "Participants" roster accepted `ConnectionRequest`s already populate (see Trip Participants above, unchanged) — `ConfirmSeatButton` remains generalized via a `{ id, kind }` pair so one component serves both.
- **`PATCH`/`DELETE /api/trips/[id]` both account for `SeatOffer`-consumed seats too**, alongside `ConnectionRequest`: `PATCH`'s consumed-seats total counts accepted `SeatOffer`s (always 1 seat each); `DELETE` (cancel trip) also flips pending `SeatOffer`s to `cancelled` and notifies both pending- and accepted-recipients (accepted ones keep their historical record untouched, same "don't delete historical data" precedent as `ConnectionRequest`).

## Removed: Request/Trip Matching Lifecycle and Reviews

This project used to have a standalone `Request` model (`tripId = null`, "requester posts first") that could get matched to a `Trip` via `requests/[id]/{accept,decline,complete}`, and a `Review` feature keyed off a completed `Request`. **Both were removed entirely**, per direct product decision that the standalone "Need a Ride"/"Need to Split an Uber" posting flow (`Request`) "is essentially not useful... and over-complicates it" — see Trip Categories & Package Carrying above. `Review.requestId` was a required FK with no Trip-based alternative, so Review had no way to survive Request's removal and was deleted along with it rather than redesigned. There is no review/rating feature, no `/requests/*` route, and no `/api/reviews` route anywhere in the app today. `ConnectionRequest` (Trip Participants, above) is a **completely different, unrelated** model and was not touched by this removal.

## Report a User

A user can report another user, optionally in the context of a trip, package post, or message thread, for **manual** admin review — there is no admin/moderator concept or moderation queue UI anywhere in this app yet, so `POST /api/reports` has zero automated consequence of any kind: no suspension, no notification, no email, no report-count surfaced anywhere (not on a profile, not anywhere else). A `Report` row is `status = open` on creation and stays that way until someone edits it directly via Prisma Studio/DB access — nothing in this feature ever transitions it. Per the plan doc's Flow F ("Report enters an admin moderation queue — manual review for MVP"), this is intentionally write-only.

- **`ReportButton`** (`src/components/ReportButton.tsx`) is the one shared control, mounted from four places, each passing a different `contextType`/`contextId` pair: `/profile/[userId]` (`"profile"`, no `contextId` — there's no separate entity beyond the user itself), `/trips/[id]` (`"trip"`, the trip's id), `/package-posts/[id]` (`"package"`, the package post's id), and `/messages/[id]` (`"message"`, the **conversation's** id, not a single message — the product framing is "report this person, in the context of this thread," not "report this one message"). Each mount is gated so a user never sees a control to report themselves (`viewer.id !== userId` on the profile page, `!isOwner` on trip/package, `counterpart &&` on messages — every conversation is 2-party, so `counterpart` is always the other person). Trip/package mounts are deliberately **not** further gated by upcoming/active status, unlike `ConnectionRequestButton` — reporting someone's behavior should stay possible even once their post is cancelled or completed.
- Same reveal-on-click composer shape as `ConnectionRequestButton` (reusing its `.connection-request-compose` CSS class as-is), but **no `confirm()` dialog**: submitting isn't destructive to the reporter and has zero automated consequence for the reported user, unlike `DeletePostButton`'s confirm()-gated actions (all irreversible changes to the caller's *own* resource). The friction gate instead is a **required** reason `<select>` with no default, same "can't submit with one click" bar `ConnectionRequestButton`'s own required note now uses.
- **`POST /api/reports`**: `reporterId` always derived from `getCurrentUser()`, never trusted from the body, same non-spoofable pattern as `POST /api/connection-requests`. `reason` is a small fixed vocabulary (`spam` / `harassment` / `unsafe_behavior` / `scam_or_fraud` / `inappropriate_content` / `other`) even though `Report.reason` is a plain `String` column with no DB enum — free-form nuance belongs in the optional `detail` field instead; a fixed set is what keeps a future moderation queue scannable without a migration. Rejects a self-report (`reportedUserId === caller.id`) with **400**, not 403 — this codebase reserves 403 for "wrong caller against someone else's resource" and uses 400 for "can't target your own X" (matching `POST /api/connection-requests`'s "can't request to connect on your own trip"). 404s if `reportedUserId` doesn't resolve to a real `User` (avoids a raw FK-violation 500 at insert time). `contextId` is deliberately **never** validated against the underlying `Trip`/`PackagePost`/`Message` — those rows can legitimately be cancelled/deleted later and a report should still stand as history. No DB-level uniqueness on `(reporterId, reportedUserId)` — the same reporter can file more than one report against the same user (different incidents), same "not worth a partial unique index" calibration as `ConnectionRequest`.
- **Explicitly out of scope**: no admin/moderation UI or route of any kind, no automated suspension or other consequence taken on a report regardless of volume or reason, no report-specific rate limiting — `src/lib/rate-limit.ts` now also covers messages and family invites (added by a later security audit, see the Messaging and Family Page sections), but reports specifically still have none, a known, deliberately deferred gap, not an oversight.

## Block a User

Implements the plan doc's Flow F "Block" half (§7, Decisions Log #13) — a one-directional `Block` row (`blockerId` → `blockedId`, already in `prisma/schema.prisma` pre-migration, no schema change needed to build this) that is **enforced bidirectionally** everywhere it matters: a blocked user disappears from the blocker's Explore results *and vice versa*, and neither party can start a new conversation or connection request with the other, regardless of who initiated the block. Unlike Report, blocking has a real, immediately visible effect and is fully reversible (unblock).

- **`src/lib/blocks.ts`** is the single place the bidirectional check lives: `isBlockedBetween(userIdA, userIdB)` (used by every route/page gate below) and `getBlockedCounterpartIds(userId)` (used once by Explore to filter its Trip query).
- **`BlockButton`** (`src/components/BlockButton.tsx`) is mounted in the exact same four places as `ReportButton` (`/profile/[userId]`, `/trips/[id]`, `/package-posts/[id]`, `/messages/[id]`), each server component computing `initialBlocked` via `isBlockedBetween` so the button renders as "Block user" or "Unblock user" without a client-side fetch. Unlike `ReportButton`, this **is** `confirm()`-gated — blocking has a visible effect on both parties — but the copy frames it as reversible ("You can unblock them later"), not as a `DeletePostButton`-style irreversible warning.
- **`POST /api/blocks`** (body `{ blockedId }`): `blockerId` always derived from `getCurrentUser()`, never the body, same non-spoofable pattern as `POST /api/reports`. Self-block is 400 (not 403, matching the existing "can't target your own X" convention), a nonexistent `blockedId` is 404. A duplicate block is a plain `upsert` no-op, not a 409 — there's no "try blocking again" flow worth protecting the way `ConnectionRequest`'s pending-duplicate check is.
- **`DELETE /api/blocks/[blockedId]`** (unblock): scoped `deleteMany({ blockerId: caller, blockedId })` where 0 rows affected → 404, the same `updateMany`/`deleteMany`-as-authorization idiom already used by `POST /api/conversations/[id]/read` and `POST /api/notifications/[id]/read`. No `GET /api/blocks` route exists — the one place blocked users are listed (`/profile`'s "Blocked Users" section) is a server component and queries Prisma directly, the same convention `/my-posts`/`/connections` already use.
- **Enforcement points**: `POST /api/conversations` and `POST /api/connection-requests` both reject (403) if `isBlockedBetween(caller, trip.travelerId)`; `POST /api/connection-requests/[id]/accept` re-checks the same thing between `requesterId`/`recipientId` as defense-in-depth, since a block can happen after a request goes pending but before it's accepted — accepting would otherwise create exactly the new `Conversation` a block is supposed to prevent. `/explore` filters its Trip query with `notIn: blockedUserIds` alongside the existing `not: user.id` self-exclusion.
- **Deliberately not touched**: existing `Conversation`/`Message`/completed-trip history that predates a block stays fully visible and usable — only *new* conversations/connection requests are blocked. Trip/package *detail pages* (as opposed to Explore) aren't hidden from a blocked counterpart either — only "search/Explore" is.

**Payment safety notice**: `/messages/[id]` (`src/app/messages/[id]/page.tsx`) renders a static `.chat-safety-notice` banner above every conversation thread, every time it's opened — reminding both parties that any money (gas contribution, delivery fee, etc.) is handled in person at the time of the ride/pickup, since this app has no payment/escrow infrastructure at all (see "No payment fields" below). It's plain server-rendered markup with no dismiss/acknowledge state — the goal is that the warning is always the first thing visible above the chat, not a one-time interstitial to click past.

## Architecture Summary

**Core entities** (`prisma/schema.prisma`): `User`, `VerificationRecord`, `SupportedUniversityDomain`, `StudentRecord`, `ParentStudentOtpRequest`, `ParentStudentInvite`, `ParentStudentLink`, `Region`, `City`, `RouteCommunity`, `Trip` (personal_car/uber_share categories, see Trip Categories & Package Carrying), `PackagePost` (the standalone, deliberately minimal package model), `Conversation`/`ConversationParticipant`/`Message`, `ConnectionRequest`, `SeatOffer`, `Notification`, `Report`, `Block`, `GeocodeCache` (caches a free-text place name -> real coordinates lookup, see the Explore Page section's Route map entry). There is **no** `Request` or `Review` model — both were removed (see Trip Categories & Package Carrying above); don't reintroduce either without re-reading why they were removed.

**Design principles baked into the schema — do not casually "simplify" these away:**
- **Verification is composable, not singular.** `VerificationRecord.type` (`email` | `university` | `parent_relationship` | `identity`) lets badges exist independently. University verification is a hard product-level gate on student accounts, enforced in application logic — not a schema constraint — so a future `identity` (government ID) verification type slots in without migration.
- **Role lives on the action.** `Trip.travelerId` doesn't care whether the user is a student, parent, or alumni.
- **A `User` account and a `StudentRecord` are separate concepts.** A `StudentRecord` can exist with no `User` at all (a parent created it first) — see the Parent/Student Linking section below. Parents now fully self-signup (no invite required); `ParentStudentLink` is purely a verification fact, never an access grant — there is no capability anywhere in the app gated on link status, since the one that used to be (posting a Trip "for" a student via the old `Request.beneficiaryId`) no longer exists.
- **Routes are open, not gated.** `RouteCommunity.active` controls what Home *features* by default (Bay Area ↔ UCI), not what can be posted — `Trip`/`PackagePost` can use any `City`, including ones outside the seeded regions (e.g. an airport for a UCI→LAX post).
- **No payment fields.** `Trip.tripNotes` is free text describing the trip itself (e.g. "driving my own car"), never a contribution/gas-money mechanism — MVP explicitly excludes payment infrastructure.
- **Anti-spam:** cap of 10 new `Trip`/`PackagePost` creations per user per rolling 12-hour window (`src/lib/rate-limit.ts`).
- **Row Level Security is enabled on every table (migration `20260910162626_enable_rls_all_tables`), with zero policies defined — this is not the app's authorization mechanism.** Every "no Postgres RLS" statement elsewhere in this doc is about *authorization*, which still lives entirely in application code (`getCurrentUser()` + explicit ownership checks in each route) exactly as described — that's unaffected, because Prisma connects as the `postgres` role, which has `rolbypassrls = true` and so is untouched by RLS regardless of what policies exist. What RLS-with-no-policies actually does is close off Supabase's auto-exposed PostgREST REST API (`https://<project>.supabase.co/rest/v1/<table>`): without it, anyone holding the project's anon key (public by design, shipped in client-side JS) could query or write any table directly, bypassing every authorization check this app's route handlers perform. Nothing in this codebase uses that REST API or the Supabase JS client for table data (Storage uploads go through the service-role admin client instead, which also bypasses RLS) — so this is a pure REST-API lockdown, safe to leave with no policies, not a partial migration toward DB-enforced authorization.

**API modules** (`src/app/api/**`), one per backend concern per the modular-monolith design:
`verification/university`, `family/invite`, `family/link`, `profile`, `trips`, `package-posts`, `conversations`, `connection-requests`, `seat-offers`, `notifications`, `reports`, `blocks`. **Every module in this list is implemented** — `profile`, `trips` (create/get/edit/cancel/complete), `package-posts` (create/get/edit/cancel/complete — deliberately no matching/accept lifecycle, see Trip Categories & Package Carrying), `conversations` (list/create/get, plus polled + posted messages), `connection-requests` (create/accept/decline/cancel), `seat-offers` (create/accept/decline/cancel/release-seat — see the Seat Offers section), `notifications` (mark one/all read), `reports` (create, manual-review-only), `blocks` (create/unblock, enforced bidirectionally — see the Block a User section), and `family/invite`/`family/link` (both linking directions — invite/accept and otp_verified→approved — see the Family Page and Parent Link Approval sections). **Windows dev-server gotcha, confirmed this session:** if `npm run dev` is ever force-killed (`Stop-Process -Force`, Task Manager, a crashed terminal) rather than allowed to exit normally, the webpack persistent cache under `.next/cache` can end up torn. The symptom is oddly specific and easy to misread as an application bug: one particular route consistently 500s with `Jest worker encountered N child process exceptions, exceeding retry limit` in the server log, while the exact same Prisma query run standalone (outside Next.js) succeeds instantly — i.e. the data layer is provably fine and it's still failing. Fix: stop the dev server and `rm -rf .next` before restarting. Avoid force-killing `next dev` when there's a graceful alternative (closing the terminal / normal Ctrl-C) to reduce how often this recurs.

**Another Windows gotcha, also confirmed this session:** running `npm run build` while `npm run dev` is still live on the same working tree corrupts the dev server's `.next` state too (a different mechanism than the force-kill case above — a build/dev collision, not a torn cache from an unclean shutdown) — the symptom is the running dev server's pages keep returning 200 but silently stop applying CSS (`<link>` tag present, stylesheet 404s or serves stale/empty content). Same fix: stop the dev server, `rm -rf .next`, restart. Check `Get-NetTCPConnection -LocalPort 3000` (or equivalent) before running `npm run build` if a dev server might still be up, rather than assuming it isn't.

**`npm run lint` is not actually configured in this project** — confirmed this session: there is no `eslint.config.js`/`.mjs` or legacy `.eslintrc.*` file anywhere in the repo, despite `eslint`/`eslint-config-next` being listed in `package.json`'s `devDependencies` and the `lint` script existing. Running it drops into `next lint`'s interactive first-time-setup prompt ("How would you like to configure ESLint?"), which hangs forever in a non-interactive shell/CI. This is a pre-existing gap, not something any feature branch broke — don't assume `npm run lint` passing (or even running) as part of verifying a change until someone deliberately sets up a config file.

## Automated Tests

Vitest, added incrementally starting with pure business-logic functions that need no database — `MANUAL_TESTING.md` was the *only* test coverage in this project before this, and stays the coverage for anything that needs a browser/DB/auth session; these two are complementary, not a replacement of one by the other. Config is `vitest.config.mts` (the `.mts` extension, not `.ts`, avoids Vite's "ESM syntax loaded as CommonJS" warning without needing `"type": "module"` in `package.json`) — Node environment, no jsdom/React plugin yet since nothing tests components. `resolve.tsconfigPaths: true` lets test files use the same `@/lib/...` aliases as app code, reading `tsconfig.json` directly rather than a separate mapping (this replaced an initial `vite-tsconfig-paths` plugin choice once Vitest 4's own Vite version flagged native support for the same thing — dropped the extra dependency).

- **Convention**: colocated `*.test.ts` files sit directly next to the source file they test (e.g. `src/lib/postStatus.test.ts` next to `src/lib/postStatus.ts`), not a separate `tests/`/`__tests__/` directory — easiest to find, and matches this project's existing colocation habits elsewhere (migrations next to schema, forms next to their pages).
- **Part 1, deliberately scoped to functions with zero DB dependency**: `postStatus.ts` (`tripDisplayStatus`, using `vi.useFakeTimers()`/`vi.setSystemTime()` since it derives from `new Date()` internally rather than taking "now" as a parameter), `otp.ts` (`generateOtpCode`/`hashOtpCode`/`generateObjectionToken` — format and determinism checks on the crypto primitives, not the DB-backed request/confirm routes that use them), `postSchemas.ts` (`tripFieldsSchema`/`packagePostFieldsSchema`, including the "exactly one of destinationCityId/destinationText" `.refine()`), `notifications.ts` (`notificationLink`/`truncateForNotification` only — every `NotificationType` case gets its own assertion, deliberately exhaustive so a future added type without a matching test forces a decision, not silently falls through the `default` case; `createNotification`/`getUnreadNotificationCount` are DB-backed and untested here), and `messaging.ts` (`isConversationUnread` only, same DB-vs-pure split as `notifications.ts`).
- **Importing a file that also exports DB-backed functions is safe**: e.g. `notifications.test.ts` imports the whole `notifications.ts` module (there's no way to import just `notificationLink` without it), which pulls in `src/lib/prisma.ts`'s `new PrismaClient()` at module load — confirmed this doesn't require `DATABASE_URL` or attempt a real connection, since Prisma Client only connects lazily on first query and none of these tests ever call a DB-backed export.
- **Part 2, the same zero-DB scoping applied to two more files**: `lookingFor.ts` (`isLookingForValue`/`lookingForLabel`) and `auth.ts`'s six pure, derived-value helpers (`isUniversityVerified`, `universityBadgeLabel`, `parentRelationshipBadgeLabel`, `hasLinkedStudent`, `hasCompletedOnboarding`, `hasStudentRecord`) — `getCurrentUser()` and `canActOnBehalfOf` stay untested here, since both are DB-backed.
- **`src/lib/testFixtures.ts`**: the shared fixture factory these `auth.ts` tests need (not itself a `*.test.ts` file, so Vitest never tries to run it as a suite). `CurrentUser` is inferred from `getCurrentUser()`'s Prisma query shape (`User` + the `verifications`/`parentLinksAsParent`/`homeCity`/`studentRecord` includes) — a literal object satisfying it needs every one of those fields, so `makeUser()`/`makeVerification()`/`makeStudentRecord()`/`makeParentLink()` supply full, sensible defaults for the whole shape and let each test override only the 1-2 fields it actually cares about. Worth knowing before extending this: `parentLinksAsParent[].studentRecord.universityDomain` and the top-level `studentRecord.universityDomain` are **not** the same shape in `getCurrentUser()`'s query — the former's `include: { universityDomain: true }` omits `region`, the latter's `include: { universityDomain: { include: { region: true } } }` includes it — `makeStudentRecord()` returns the wider (with-`region`) shape and gets reused for both call sites, which type-checks fine (structural typing allows an already-typed value with extra fields to satisfy a narrower target — excess-property checks only fire on fresh object literals), but don't assume the two are interchangeable if you're reading Prisma's own generated types directly. Keeping this factory in sync with the `User`/`StudentRecord`/etc. models is the tradeoff for the convenience — a schema change that breaks it fails loudly at compile time, not silently.
- **Part 3, two more pure functions plus one extraction done specifically for testability**: `email.ts`'s `escapeHtml()` (exported for this purpose — it was previously module-private) got a dedicated test given it's a deliberate XSS mitigation. `src/lib/supabase/middleware.ts`'s redirect decision was pulled out into a standalone exported predicate, `shouldRedirectToParentLinkGate({ isAuthenticated, isSignedUpAsParent, hasLinkedStudentFlag, isApiRoute, pathname })`, so the parent-link gate's actual branching logic is unit-testable without faking a `NextRequest`/`@supabase/ssr` session — `updateSession()` itself just gathers those five inputs and calls it. `geo.ts`'s route-pair-matching functions were deliberately **not** given a similar extraction — their "logic" is just the Prisma `WHERE` clause itself, no separable pure part worth pulling out; those are covered by the DB-backed suite below instead.
- **DB-backed suite** (`*.db.test.ts` files, run via `npm run test:db`, NOT picked up by plain `npm test` — see `vitest.config.mts`'s `exclude` and the separate `vitest.config.db.mts`): resolves the "not yet decided" question above — a disposable local Postgres via Docker (`docker-compose.test.yml`, `npm run db:test:up`/`db:test:down`), never the shared Supabase dev database and never a mocked Prisma client, since the whole point is exercising real transaction/race behavior. `.env.test` (committed — see its own header comment for why that's safe) holds the connection string; `npm run test:db`'s `pretest:db` hook runs `prisma migrate deploy` against it first via `dotenv-cli`. `src/lib/testDb.ts` (not a `*.test.ts` file, same non-suite convention as `testFixtures.ts`) has a load-bearing safety guard that throws at import time if `DATABASE_URL` doesn't look like the disposable test DB, plus `resetTestDb()`/`resetAndSeed()` (`TRUNCATE ... CASCADE` across every table, enumerated from the Prisma DMMF so it can't drift out of sync with the schema, called in each suite's `beforeEach`). `src/lib/testDbFixtures.ts` (separate from `testFixtures.ts`, which must stay Prisma-free) holds real-insert factories (`createUser`, `createTrip`, `createConnectionRequest`, etc.) that auto-create required FK parents and reuse `testFixtures.ts`'s `makeUser()` for default field values. `vitest.config.db.mts` sets `fileParallelism: false` since every file shares one truncated-per-test Postgres instance. For an auth-gated route handler, `getCurrentUser` is mocked (`vi.mock("@/lib/auth", ...)`, preserving other real exports like `hasStudentRecord`) with its resolved value's `id` matching a real DB-inserted `User` — everything else (Prisma queries, the transaction itself) runs for real; Next 15's dynamic route params are a `Promise`, so tests pass `{ params: Promise.resolve({ id }) }`. Current coverage: `onboarding.db.test.ts` (both `claimOrCreateStudentRecord` races, plus `syncUserFromAuth` idempotency), the two overbooking-prevention routes (`confirm-seat`, `seat-offers/[id]/accept` — each asserting a concurrent pair of calls never oversells a trip; a third, `requests/[id]/accept`, was removed along with the standalone `Request` model it tested — see Trip Categories & Package Carrying above), `rate-limit.db.test.ts` (all three rolling-window functions, including window-boundary exclusion), `blocks.db.test.ts`, `profile.db.test.ts`, and one representative of the `updateMany`-as-authorization-only family (`conversations/[id]/read`) — the rest of that family (`archive`/`unarchive`/`DELETE conversations/[id]`, `notifications/[id]/read`) is lower-risk and not yet covered, a reasonable follow-up rather than a gap. CI (`.github/workflows/ci.yml`) runs both suites plus `npm run build` on every push/PR to `main`, via a Postgres service container rather than Docker-in-Docker.

## Environment Variables

Copy `.env.example` to `.env` (never fill real values into `.env.example` itself — it's committed to the repo) and fill in:
- `DATABASE_URL` / `DIRECT_URL` — Postgres connection strings (Supabase provides both). See the comments in `.env.example` for two non-obvious gotchas already hit once: `DATABASE_URL` needs `?pgbouncer=true` (transaction-pooler prepared-statement conflicts), and `DIRECT_URL` should point at the session pooler (port 5432, same host as `DATABASE_URL`) rather than Supabase's plain `db.<ref>.supabase.co` host, which is IPv6-only and unreachable from IPv4-only networks.
- `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` — Supabase client config
- `SUPABASE_SERVICE_ROLE_KEY` — server-only, never expose to the client. Used by `src/lib/supabase/admin.ts`, which now backs several things beyond its original one purpose: parent signup's pre-confirmed account creation, avatar uploads (`src/lib/supabase/storage.ts`), and setting/clearing the `hasLinkedStudent` `app_metadata` flag the parent-link gate's middleware check reads (see Auth Architecture).
- `RESEND_API_KEY` / `EMAIL_FROM` — transactional email for verification + invite links. Optional in development: without it, `src/lib/email.ts` logs the email (verification link, OTP code, objection/invite token, whatever the email actually contains) to the console instead of sending it, which is fine for local dev but would leak that same sensitive content into log storage if it ever happened in production. `send()` in `email.ts` now checks `NODE_ENV` and throws instead of console-logging when `RESEND_API_KEY` is missing and `NODE_ENV === "production"` — so this key is effectively **required** in any production deploy, not just recommended; a misconfigured deploy fails loudly instead of silently leaking secrets to logs.
